# Implementation plan: daily own-checks and inspection documentation

Technical plan for the **egenkontrol** module: daily food-safety own-checks (HACCP controls),
their audit trail, an overview, and documentation that can be presented to the Danish
Veterinary and Food Administration (Fødevarestyrelsen).

This is a **new module**. `docs/mcdonalds-gap-implementation-plan.md` explicitly parks
"Operations (SOD/EOD, tasks, egenkontrol, temperatures)" as out of scope; this plan picks up
exactly that piece and nothing else. It does not depend on any task in that plan, and it does
not change any existing feature apart from four shared registries (permissions, sidebar,
kiosk destinations, storage cleanup).

The document is English; every string it tells you to ship is Danish.

## Decisions already made

Settled. Do not re-litigate while implementing.

1. **Pending occurrences are derived, not materialized.** A scheduled own-check that nobody
   has performed has **no row**. The expected plan for a day is computed from versioned
   templates by a pure function, the same way `lib/count-window.ts` derives count windows.
   Rejected alternative: a daily cron that writes one row per template per location per day.
   That cron is a single point of failure for a compliance feature (a missed run silently
   erases the evidence that a check was ever required), it multiplies writes by
   locations × templates × days, and Convex crons are UTC while due times are location-local.
2. **Template history is versioned and append-only.** Editing a template closes the current
   version (`validTo`) and inserts a new one. Expansion for a past date uses the version that
   was valid *on that date*, so an export never claims that yesterday required today's checks.
   This is what makes decision 1 safe.
3. **Submitted records are immutable.** Every mutation that touches a submitted record appends
   a full snapshot to `ownCheckEntryRevisions`. Revision 1 is always the original submission
   and is never rewritten. The entry row carries the latest snapshot only so it can be indexed
   and filtered.
4. **Compliance is decided on the server.** The client may compute the same verdict for
   instant feedback, but `submitOwnCheck` recomputes limits from the stored template version
   and overwrites whatever the client claimed.
5. **Own-checks are not blocked by the count lock, unless an organization asks for it.**
   `lockOtherFeaturesDuringCount` (`convex/lib/countLock.ts`) does not gate this module by
   default. The behaviour is exposed as `ownCheckSettings.blockDuringCount`, default `false`.
   The product owner chose to make it configurable with the risk stated: enabling it makes a
   food-safety control unavailable while a stock count is open. The settings UI must carry a
   Danish warning saying exactly that, and the default must never be flipped in code.
6. **Exactly one new dependency: `pdf-lib`.** Approved by the product owner on 12 August 2026
   specifically for this module, overriding the general "avoid adding dependencies" rule in
   `AGENTS.md`. The inspection document is a real PDF generated by us, not a browser print, so
   pagination, headers and photo placement are identical on every machine. CSV
   (`lib/download-csv.ts`) ships alongside it. The ZIP bundle stays optional and uses the
   already-installed `fflate`. Do not add anything else.
7. **Own-check photos are stored as JPEG or PNG.** `pdf-lib` can only embed those two. The
   client re-encodes to JPEG before upload and the server rejects anything else (plus
   `application/pdf` for supporting documents, which `pdf-lib` merges via `copyPages`).
8. **Own-check records are never pruned.** The 400-day `auditLog` prune
   (`convex/audit.ts:5`, `convex/crons.ts:37`) must not be extended to `ownCheckEntries`,
   `ownCheckEntryRevisions`, or `ownCheckAttachments`.
9. **All three pages are kiosk destinations, and the organization decides which are on.**
   Today, overview *and* documentation are registered in `lib/kiosk.ts`, so an inspector can be
   handed the tablet. Be explicit about what this costs: `requirePermission`
   (`convex/lib/auth.ts:257`) *returns early* when a kiosk destination matches, so a tablet with
   the documentation page enabled can export inspection data without holding
   `ownChecks.export`. That is the intended trade, it is opt-out per organization in the
   existing kiosk settings, and the settings UI must say so in Danish (task 1).
10. **Managers may amend submitted records.** `ownChecks.edit` stays in the `manager` default.
    Every amendment still requires a reason and still appends a revision — the control is the
    audit trail, not the scarcity of the permission. No age limit on amendments.
11. **Approval is four-eyes by default, and switchable per organization.**
    `ownCheckSettings.requireSecondPersonApproval`, default `true`: the user who performed a
    check cannot approve it, unless their role also holds `ownChecks.manage` — the escape
    hatch for locations staffed by one person. Set it to `false` and self-approval is allowed.
    Independently of the setting, approval is impossible while a deviation has no corrective
    action; that rule is not configurable.
12. **`responsibleRole` is informational, never a gate.** Anyone with `ownChecks.perform` for
    a location may complete any check scheduled there. The template's responsible role drives
    labels, the overview's responsible filter and the missing-checks list — it must not be
    turned into a server-side restriction. A food-safety control that cannot be filed because
    the assigned person is off sick is a control that gets filed under someone else's login.
13. **Three policy rules live in `ownCheckSettings`, the rest are fixed.** Configurable:
    the late-submission window, four-eyes approval, and the count-lock behaviour. Not
    configurable, and not to be made configurable without a new decision here: a deviation
    always requires a description, an amendment always requires a reason, approval always
    waits for a corrective action, and the range caps stay in code.
14. **Approved records are closed.** An approved record cannot be edited or receive a new
    corrective-action revision. A correction requires a separately designed superseding-record
    flow; an ordinary amendment must never silently invalidate an approval.

## Rules that apply to every task

- All user-facing text is **Danish**. Status labels, control types, validation errors,
  CSV headers, PDF headings.
- Every record is scoped by `organizationId` and every read is filtered through
  `resolveLocationFilter` / `requireLocationAccess` (`convex/lib/auth.ts:213-243`).
- Permission checks live in `convex/lib/auth.ts` and `lib/auth-permissions.ts`. Never
  re-implement a check inside a module.
- Read `convex/_generated/ai/guidelines.md` before writing Convex code. Argument **and**
  return validators on every function; `withIndex`, never `.filter()` as the primary access
  path; `ctx.db.get("table", id)` followed by an `organizationId` equality check.
- Use shadcn/ui; invoke the `shadcn` skill when creating UI. Tablet-first: ≥44 px touch
  targets, one-thumb reach for the primary action, keyboard navigable.
- Money is not involved here, but the same discipline applies to measurements: store numbers
  as entered plus the unit label; never round on write.
- Danish decimal comma in the UI and in CSV, dot in storage (see the `String(x).replace(".", ",")`
  convention in `components/waste/waste-report.tsx:256`).

Semantics, to be enforced identically everywhere:

| Permission | Grants |
| --- | --- |

| `ownChecks.correct` | Record or amend the corrective action on a record with a deviation |
| `ownChecks.view` | Read historical records and their revision history |
| `ownChecks.approve` | Approve a record (only when no deviation is open) |
| `ownChecks.edit` | Amend a submitted record's values; always creates a revision and always requires a reason. In the `manager` default (decision 10) |
| `ownChecks.export` | Open the documentation page and export |
| `ownChecks.manage` | Create, edit, archive templates and schedules |

Rules `expandOccurrences` must obey:

- A version applies to date *D* when `validFrom <= dueAt(D) && (validTo === undefined || dueAt(D) < validTo)`.

  (callers turn it into a Danish `ConvexError`).

`Punktet skal bekræftes`, `Feltet skal udfyldes`.

Tests must cover: DST boundaries in `Europe/Copenhagen` (late March and late October — a

# Task 5 · Perform an own-check

**Model: `gpt-5.6-luna` (max), review by `gpt-5.6-terra` (high).** Depends on task 4.

## Goal

`listToday` returns today's plan for a location — expected occurrences merged with any

## Scope

  time zone, build the merged plan, write a revision).

Out of scope: UI (task 6), edit/approve (task 8), export (task 9).

## Implementation

```ts
generateAttachmentUploadUrl()                    // mutation, requireOwnCheckPerformer
listToday({ locationId: v.optional(...), dateKey: v.optional(v.string()) })   // query
submitOwnCheck({
  locationId, templateId, dueDateKey,
  values: v.array(ownCheckValueValidator),
  note: v.optional(v.string()),
  deviationDescription: v.optional(v.string()),
  correctiveAction: v.optional(v.string()),
  clientRequestId: v.optional(v.string()),
})                                                // mutation -> { entryId, status, compliant }
```

`listToday`:

1. `requireOwnCheckPerformer(ctx, ["ownChecks.today", "ownChecks.overview"])`, then
   `resolveLocationFilter` (`convex/lib/auth.ts:231`). A kiosk account is pinned to its
   location; a normal user picks one via the existing `components/location-field.tsx`.
2. `resolveTimeZone(ctx, organizationId, locationId)`.
3. `dateKey = dateKey ?? dateKeyInZone(Date.now(), timeZone)`; reject a `dateKey` more than
   366 days from today.
4. Load template versions overlapping the day via
   `by_organizationId_and_validFrom` (`gte(validFrom, dayStart - …)` is wrong — read all
   versions whose `validFrom < dayEnd` with `.take(MAX_VERSIONS + 1)` and filter `validTo` in
   memory; cap at 2000 versions and throw a Danish error above it).
5. `expandOccurrences(...)` for that single day.
6. Read entries with `by_organizationId_and_locationId_and_dueDateKey` and join on
   `templateId`.
7. Return each occurrence with its `fields`, `description`, `status`
   (`ownCheckStatus`), `dueAt`, `startsAt`, `overdue`, and the entry summary when present.

Also return, in the same query, the **overdue backlog**: occurrences from the previous
`lateSubmissionDays` days (`getOwnCheckConfiguration`, default 7) that have no entry, so the
tablet shows "Manglende kontroller" without a second round trip and shows exactly the days it
is still possible to act on. Cap it and expose a `truncated` flag. With the setting at 0 the
backlog is empty and the section is hidden.

`submitOwnCheck`:

1. `requireOwnCheckPerformer` → `requireLocationAccess`. Then, **only when**
   `configuration.blockDuringCount` is true (decision 5), call `requireOtherFeaturesUnlocked`
   the way `convex/badDeliveries.ts:403` does. Default configuration skips the check entirely,
   so an own-check is unaffected by an open count.
2. When `clientRequestId` is set, look it up on `by_organizationId_and_clientRequestId` and
   return the existing entry unchanged (idempotent retry from a flaky tablet connection).
3. Resolve the location, time zone, and the template version valid at that occurrence's
   `dueAt` — **the version, not the template's current fields.**
4. Reject a `dueDateKey` that the schedule does not produce for that location, that is more
   than `configuration.lateSubmissionDays` days in the past, or that is in the future. The
   Danish error names the window: "Egenkontrollen kan kun registreres op til 7 dage tilbage".
   Reject a duplicate on `by_org_location_template_dueDateKey`.
5. Validate values against the version's fields: every key known, no duplicates, required
   fields present, numbers finite and within ±1e9, text ≤ 2000 characters, choice values in
   the option list, attachments ≤ `maxFiles`.
6. Attachments: verify each `_storage` id via `ctx.db.system.get("_storage", id)`, content type
   in `{image/jpeg, image/png, application/pdf}` — **not** WebP or AVIF, which `pdf-lib`
   cannot embed (decision 7) — size ≤ 10 MB, and not already referenced (`by_storageId`),
   mirroring `convex/badDeliveries.ts:387-440`. Reject anything else with
   "Brug JPEG-, PNG- eller PDF-filer på højst 10 MB".
7. `evaluateCompliance` decides `compliant`. When it is false, `deviationDescription` is
   **required** (Danish error: "Beskriv afvigelsen"). A deviation may also be declared on a
   compliant result (staff noticed something) — accept that too.
8. Derive `status`/`hasDeviation`/`followUp`:
   - compliant, no deviation → `completed`, `false`, `none`
   - deviation without corrective action → `deviation`, `true`, `open`
   - deviation with corrective action → `deviation`, `true`, `resolved`
   `approved` is never set here — approval is always a separate act by a separate mutation.
9. Insert the entry with `revision: 1`, insert `ownCheckAttachments` rows with
   `addedAtRevision: 1`, insert revision 1 (`kind: "submitted"`, `changes: []`), and
   `recordAudit` with `action: "ownChecks.submitted"` and a Danish summary naming the check,
   the location and the outcome. No `reason` — the submission is not a correction.

Rate limit `submitOwnCheck` per user in `convex/lib/rateLimits.ts` (token bucket, e.g. 60 per
minute) to bound accidental client retry storms.

## Constraints

- Never trust a client-supplied `compliant` flag — the argument does not exist.
- Never read the template's *current* fields when a version id is available.
- One entry per (organization, location, template, dueDateKey).
- Everything in one transaction; a partial submission must not leave orphan attachment rows.

## Verification

- Submitting a temperature above `max` yields `status: "deviation"` and refuses to save

- Submitting the same occurrence twice returns a Danish "allerede registreret" error; retrying
  with the same `clientRequestId` returns the first entry.

- Editing the template after submission leaves the entry's `values`, `fields` snapshot and

# Task 8 · Edits, approval and corrective actions

**Model: Opus 5 (high).** Depends on task 5. This is the audit-integrity core.

## Goal

A submitted record can be corrected, approved, and completed with a corrective action — and
every one of those writes an immutable revision that preserves the previous values, the new
values, the timestamp and the actor. Nothing is ever overwritten without a trace.

## Scope

- `convex/ownChecks.ts` — `editOwnCheck`, `recordCorrectiveAction`, `approveOwnCheck`.
- `convex/lib/ownChecks.ts` — `appendRevision` helper.
- `components/own-checks/own-check-record.tsx` — the three actions.

## Implementation

`appendRevision(ctx, auth, entry, next, kind, reason?)` is the only way any of these mutations
may write. It:

1. Computes `changes` by diffing the stored snapshot against `next` with `formatValue`, using
   the template version's field labels. Deviation, corrective action, status and note changes
   each produce a change row too.
2. Inserts an `ownCheckEntryRevisions` row with `revision: entry.revision + 1`, the **full**
   post-state snapshot, the actor from `auth`, and `reason` (required, via
   `requireAuditReason`, for `kind === "edited"`).
3. Patches the entry with the new snapshot, `revision`, `updatedAt`.
4. Calls `recordAudit` with a Danish summary and, for edits, the same reason.

Guarantees to enforce inside it: `revision` increases by exactly one; revision 1 is never
patched; `hasDeviation` never goes from `true` to `false`; `performedAt`, `performedBy` and
`dueDateKey` are never modified.

`editOwnCheck({ entryId, values, note?, deviationDescription?, correctiveAction?, reason })`:

- `requireOwnCheckEditor` + `requireLocationAccess`.
- Re-validates against the **stored** `templateVersionId`, re-runs `evaluateCompliance`, and
  recomputes status. An edit that introduces a limit breach flips the record to `deviation`
  and demands a description.
- New attachments are inserted with `addedAtRevision: revision + 1`; removed ones get
  `removedAtRevision` — the storage file and the row stay (decision 3).
- Refuse to edit a record older than 400 days without `ownChecks.manage`? No — refuse nothing
  on age. Editability is a permission question, not a time question. Reason is always required.

`recordCorrectiveAction({ entryId, description })`:

- `requireOwnCheckCorrector`, entry must have `hasDeviation`.
- Sets/replaces `correctiveAction` (previous text preserved in the revision), `followUp:
  "resolved"`. No reason required for the first one; required when replacing an existing
  corrective action (that is an edit of a compliance statement).

`approveOwnCheck({ entryId })`:

- `requireOwnCheckApprover`.
- Refuse when `followUp === "open"` ("Afvigelsen skal følges op, før kontrollen kan godkendes").
  This rule is not configurable.
- Read `getOwnCheckConfiguration`. When `requireSecondPersonApproval` is true (the default),
  refuse `auth.userId === entry.performedBy` **unless** the role also holds `ownChecks.manage`
  — the escape hatch for single-person locations. When the organization has turned it off,
  self-approval is allowed. The record always names the approver either way, so the audit
  trail carries the same information under both settings. State the active rule in the UI
  help tooltip, reading it from the settings query rather than hardcoding the sentence.
- Sets `status: "approved"`, `approvedAt/By/ByName`; `hasDeviation` is untouched.

Undoing an approval is not supported. If it is ever needed, it is another revision kind, never
a patch.

## Constraints

- No mutation may call `ctx.db.patch` on `ownCheckEntries` outside `appendRevision`.
- No delete path for entries, revisions or attachments exists anywhere.
- Every one of the three mutations writes exactly one revision and one `auditLog` row.

## Verification

- Edit a record twice; the record view shows revisions 1, 2 and 3 with correct before/after
  pairs and the original values still readable in revision 1.
- Approving a record with an open deviation fails with the Danish error.
- A performer cannot approve their own record without `ownChecks.manage`.
- Removing a photo in an edit keeps the file downloadable from revision 1's attachment list.
- New tests in `convex/ownChecks.test.ts` assert revision monotonicity and that
  `hasDeviation` never clears. `bun run test`, `bun run lint`, `bun run build`.

# Task 9 · Inspection documentation

**Model: `gpt-5.6-luna` (max).** Depends on tasks 3, 7, 8.

## Goal

At `/own-checks/documentation` a user with `ownChecks.export` picks a date range and location
and gets a chronological inspection report — on screen, as a generated PDF, and as CSV —
containing every completed check with values, notes, attachments, deviations, corrective
actions and revision history, plus every missing or overdue check.

## Scope

- New `convex/ownCheckDocumentation.ts`.
- New `app/own-checks/documentation/page.tsx`.
- New `components/own-checks/inspection-documentation.tsx`, `inspection-report.tsx`.
- New `lib/own-check-pdf.ts` — the `pdf-lib` document builder.
- `package.json` — add `pdf-lib` (the one approved dependency; decision 6).

## Implementation

`buildDocumentation({ paginationOpts, fromDateKey, toDateKey, locationId })`, query,
`requireOwnCheckExporter`:

- Single location required (an inspection is of one restaurant). `requireLocationAccess`.
- Range ≤ 366 days, page size fixed like `EXPORT_PAGE_SIZE` in `convex/badDeliveries.ts:39`
  and guarded by the `requirePageSize` check at line 724.
- Page over entries with `by_organizationId_and_locationId_and_dueAt`, **ascending** —
  chronological, not the `desc` the reports use.
- Per entry return: `dueDateKey`, `dueAt`, `performedAt`, `name`, control type, status,
  `performedByName`, values rendered with their labels, units and limits, note, deviation,
  corrective action, attachment URLs with content types, and the full revision list.
- A separate `getDocumentationHeader` query returns the location name plus the masterdata that
  identifies the business (legal entity name and `registrationNumber` via
  `locations.legalEntityId`, operator, market), the period, `generatedAt`, and the requesting
  user's name — the "Each export should clearly identify" requirement. The organization name
  and logo come from the client: `useOrganization` in `components/app-shell.tsx` and
  `api.organization.getBranding` (`convex/organization.ts:64`) for the wide logo.
- A separate `listMissingOwnChecks({ fromDateKey, toDateKey, locationId })` expands
  occurrences for the range and subtracts entries, returning the missing ones with their due
  time and the responsible role. Cap at 5000 with a `truncated` flag.

UI:

- Range presets ("Denne uge", "Denne måned", "Sidste 3 måneder", custom), location picker,
  "Vis dokumentation" button.
- On screen: a header block (organization + logo, location, period, generated at/by), a
  summary line ("142 udførte kontroller, 6 afvigelser, 3 manglende"), then a chronological
  section per day with one card per record and a clearly marked
  **"Manglende egenkontroller"** section.
- "Hent PDF" builds the document with `lib/own-check-pdf.ts` (below) and downloads it as
  `egenkontrol-<lokation>-<fra>-<til>.pdf`.
- "Eksportér CSV" uses `downloadCsv` (`lib/download-csv.ts`) with one row per recorded value:
  `Dato;Tidspunkt;Egenkontrol;Kontroltype;Lokation;Udført af;Felt;Værdi;Grænse;Inden for grænsen;Status;Afvigelse;Korrigerende handling;Godkendt af;Rettelser`.
  Missing checks get their own rows with `Status = "Ikke udført"`. Filename
  `egenkontrol-<lokation>-<fra>-<til>.csv`.
- Load all pages before rendering the report (loop `usePaginatedQuery`'s `loadMore` until
  `status === "Exhausted"`, as the waste report does) and show a progress state; refuse ranges
  that exceed the cap with a Danish message suggesting a narrower period.

### `lib/own-check-pdf.ts`

Pure module, browser-only, no React. `buildInspectionPdf(input): Promise<Uint8Array>` where
`input` is the header block, the ordered records, the missing list, and the fetched attachment
bytes. Rules:

- A4 portrait, 40 pt margins, `StandardFonts.Helvetica` and `Helvetica-Bold`. Those use
  WinAnsi encoding, which covers **æ ø å Æ Ø Å** — but not every character a user can type.
  Sanitise every string through a helper that replaces unencodable code points with `?` rather
  than letting `drawText` throw mid-document, and unit-test that helper with Danish text plus
  an emoji.
- **Front page**: organization name and logo (PNG/JPEG bytes fetched from the branding URL;
  skip the logo silently if it fails), legal entity and registration number, location, the
  period, `generatedAt`, the exporting user, and the summary counts. This is the "clearly
  identify" requirement.
- **Chronological body**: a section header per date, then one block per record with the check
  name, control type, planned time, `performedAt`, performer, a values table (label, value,
  limit, "Inden for grænsen"/"Uden for grænsen"), note, deviation, corrective action, approver,
  and a compact revision list ("Rettelse 2 · 13-08-2026 09:14 · Ida Nielsen · Årsag: …").
  Deviating records get a visible marker in the margin.
- **Photos** embedded with `embedJpg`/`embedPng`, scaled to fit half the text width, placed
  after their record, each captioned with field label and file name. PDF attachments are
  appended at the end of the document with `copyPages` under a "Bilag" heading and referenced
  from their record.
- **Missing checks section** last: date, check name, planned time, responsible role.
- Page numbering "Side X af Y" and a running footer with location and period on every page,
  drawn in a final pass once the page count is known.
- Deterministic given the same input: no `Date.now()` inside the builder (`generatedAt` is an
  argument), and set `pdfDoc.setCreationDate`/`setModificationDate` from it.
- Hard caps: 5000 records, 2000 embedded images, 100 MB output. Above them, throw a Danish
  error asking for a narrower period.

Generate in a `startTransition`/worker-free async path with a progress indicator; a year of
daily checks with photos takes seconds, not milliseconds.

## Constraints

- The export must be reproducible: the same range and location produce the same document
  regardless of later template edits.
- `pdf-lib` is the only dependency this plan adds. Do not pull in a chart, font-subsetting or
  HTML-to-PDF package alongside it.
- No server-side PDF generation. It runs in the browser, so no Convex action size limits and
  no storage cost.
- Never expose an attachment URL for a location outside the caller's scope.

## Verification

- A generated PDF opens in Preview, Acrobat and Chrome; Danish characters render correctly in
  headings, values and free text.
- A record with two photos and one PDF attachment shows both images inline and the attachment
  appended under "Bilag".
- The same range exported twice produces byte-identical output for the same `generatedAt`.
- The CSV opens in Danish Excel with correct decimal commas and semicolons.
- A period containing a template rename shows the name as it was on each date.
- A user with `ownChecks.view` but not `ownChecks.export` cannot reach the page or the query;
  a kiosk tablet with `ownChecks.documentation` enabled can (decision 9).
- `bun run test` (including the string-sanitiser unit test), `bun run lint`, `bun run build`.

# Task 11 · Access tests

**Model: `gpt-5.6-luna` (max).** Depends on tasks 1, 5, 8.

## Goal

`convex/ownChecks.test.ts` proves the server-side boundary, in the style of
`convex/access.test.ts` (`convexTest` + `setupAuthOrg`, Danish test names).

## Cases

1. A member with only `ownChecks.perform` can submit but cannot read history, approve, edit or
   export.
2. A user scoped to location A cannot submit for, read, or export location B — including
   pending occurrences in the overview.
3. A kiosk account may submit for its pinned location only, and only when `ownChecks.today` is
   in `kioskSettings.enabledPages`. Separately: a kiosk account **without** `ownChecks.export`
   may run the documentation queries when `ownChecks.documentation` is enabled, and is
   rejected when it is not (decision 9). Assert both directions — this is the one place the
   plan deliberately allows a permission bypass, so it must be pinned by a test rather than
   left to a code reading.
4. A value outside `max` forces `status: "deviation"` and rejects submission without a
   description.
5. Submitting the same occurrence twice fails; the same `clientRequestId` is idempotent.
6. `editOwnCheck` without a reason fails; with one it appends revision 2 while revision 1 keeps
   the original values.
7. `approveOwnCheck` rejects the performer and rejects an open deviation; a performer whose
   role also holds `ownChecks.manage` may approve (decision 11's escape hatch); with
   `requireSecondPersonApproval: false` the plain performer may approve, and the open-deviation
   refusal still holds.
8. A template edited between two submissions leaves the first entry's snapshot unchanged.
9. A default `manager` role can edit a submitted record with a reason, and a default `member`
   role cannot (decision 10).
10. `lateSubmissionDays: 0` rejects yesterday's occurrence and accepts today's; the default
    accepts an occurrence 7 days back and rejects one 8 days back.
11. `blockDuringCount: false` (the default) lets a submission through while a count locks the
    location; `true` rejects it. Both directions asserted — this setting can make a
    food-safety control unavailable, so it must not drift.
12. An organization with no `ownCheckSettings` row behaves exactly as 7 / true / false.

## Verification

`bun run test` — all new tests pass and the existing 12 in `convex/access.test.ts` still do.

# Notes for whoever implements this

- **Decisions 1–3 are the plan.** Derived pending state, versioned templates, append-only
  revisions. Everything else is mechanical. If a task tempts you to patch a template version
  in place or to write a nightly cron that materializes occurrences, stop and re-read them.
- **Task 2's `storageCleanup` line is easy to forget and expensive to miss.** Without it,
  every inspection photo is deleted 24 hours after upload.
- **Task 3 before anything else that touches dates.** DST at 23:59 on the last Sunday in
  October is a real Copenhagen case, and the count module's hardcoded time zone is not a
  pattern to copy.
- Tasks 1 and 2 are additive and unblock four parallel tracks. Land them first, together.
- The riskiest review is task 8. Give it to `gpt-5.6-sol` (high) as a read-only pass with the
  brief: "prove that no code path can overwrite or delete a submitted own-check value."
- **`pdf-lib` is the only dependency this plan buys.** It was approved for the inspection
  document specifically. If task 9 starts wanting a second package, that is a signal the PDF
  layout is being over-designed — cut the layout, not the budget.
- **Decision 7 has to be enforced at upload time, not at export time.** A WebP photo that
  reaches storage is a photo that cannot go into the PDF, and by then the record is immutable.
  Task 5's content-type check and task 6's `compressImage` change are the same requirement
  seen from two sides; land them together.
- **Decision 9 is a deliberate hole in the permission model.** It is opt-out per organization
  and it is covered by a test in task 11. Do not "fix" it during a review pass without talking
  to the product owner.
- **`blockDuringCount` is the one setting that can hurt someone.** It exists because the
  product owner asked for it with the risk on the table. Default `false`, warned in the UI,
  confirmed by a dialog, and asserted in both directions by a test. Do not let a later
  refactor quietly move the default.
- **Nothing outside `getOwnCheckConfiguration` may know a policy default.** The moment a
  second module writes `?? 7`, the settings page starts lying.
- **Granting the new permissions needs no UI work.** `role-permissions.tsx:286` renders
  `permissionCatalog`, and `kiosk-settings.tsx:282` renders `kioskDestinations`. Task 1's
  registry entries are the whole administration surface for who may do what.
