# Google and Wolt location scores and reviews

As of 2026-08-27

This note assesses documented first-party and third-party ways for a multi-restaurant SaaS to show a chain's per-location scores and customer reviews. It separates provider APIs, reputation platforms, merchant portals, and public-web collection. It is a product and contract assessment, not legal advice.

## Executive conclusion

Google has a documented owner-authorized path. The Google Business Profile (GBP) Reviews API can return a verified location's `averageRating`, `totalReviewCount`, and paginated individual reviews. It requires Google API access, OAuth authorization, and a user who can access each location. [Reviews list reference](https://developers.google.com/my-business/reference/rest/v4/accounts.locations.reviews/list) [OAuth overview](https://developers.google.com/my-business/content/oauth-overview) [API prerequisites](https://developers.google.com/my-business/content/prereqs)

That path is technically supported for a live, per-location view after API approval, merchant authorization, and data-handling review. It is not automatically cleared for a durable review warehouse, historical trend series, or cross-location aggregate. GBP policy limits how API content may be prefetched, cached, stored, manipulated, and aggregated, including a temporary-storage limit of no more than 30 calendar days. [Google Business Profile API policies](https://developers.google.com/my-business/content/policies)

Google Maps Platform Places API (New) is a separate public-data path. Place Details can return a current `rating`, `userRatingCount`, and at most five `reviews`; ratings and reviews are billable fields and review display requires attribution and a Google Maps link. Places content is not a durable application database, although a `place_id` may be stored indefinitely. For an EEA-billed white-label SaaS, the permitted-use terms create an additional unresolved issue: the listed use case covers a customer's own physical stores, while this product displays client restaurants through a shared SaaS. Do not use Places as a fallback until Google confirms that setup in writing. [Place Details](https://developers.google.com/maps/documentation/places/web-service/place-details) [Places policies](https://developers.google.com/maps/documentation/places/web-service/policies) [EEA Places permitted uses](https://cloud.google.com/terms/maps-platform/eea-places-api-permitted-uses)

Wolt's public merchant materials show that merchants can see a rating and written reviews in Merchant Portal. Its public webhook guide also lists an optional `REVIEW` notification when a consumer provides a review or rating for an order, but does not define a review object, canonical score read endpoint, or complete review export. Wolt's Denmark consumer terms prohibit automated collection or copying from the service without Wolt's consent and limit access to expressly provided interfaces. Browser scraping and undocumented `wolt.com` requests are therefore unsupported. [Wolt developer documentation](https://developer.wolt.com/docs) [Wolt webhook guide](https://developer.wolt.com/docs/webhook) [Wolt Merchant Portal rating guide](https://merchant.wolt.com/en/dnk/learning-center/how-to-improve-your-venue-rating-on-wolt) [Wolt Denmark terms](https://explore.wolt.com/en/dnk/terms)

Third-party research did not identify one documented, licensed vendor that solves both sources. ReviewTrackers, Uberall, and Yext are credible Google aggregation candidates with APIs and partner tooling, but none publicly documents Wolt review coverage. Bright Data advertises technical collection for both Google Maps and Wolt, but that is scraping, not a provider-authorized review feed or a grant of downstream display rights. The Wolt side therefore remains blocked without Wolt's written consent, even if a data vendor can return the fields. [ReviewTrackers API](https://www.reviewtrackers.com/blog/api-integrations/) [ReviewTrackers sources](https://www.reviewtrackers.com/sites-we-monitor/) [Uberall reputation API](https://docs.uberall.com/guides/reputation-management) [Yext Reviews API](https://docs.yext.com/docs/managementapis/reviews/reviewmanagement) [Bright Data Wolt scraper](https://brightdata.com/products/web-scraper/wolt) [Wolt Denmark terms](https://explore.wolt.com/en/dnk/terms)

The resulting product decision is:

- Conditional go: Google GBP per-location score, count, and reviews for locations the merchant authorizes. Ship only after API approval and confirmation of the exact cache, retention, and display design. [GBP Reviews API](https://developers.google.com/my-business/reference/rest/v4/accounts.locations.reviews/list) [GBP API policies](https://developers.google.com/my-business/content/policies)
- Do not use as the default fallback: Places can provide a current public snapshot, but its five-review limit, billing, storage rules, and EEA permitted-use ambiguity make it a poor fit for this dashboard. Google historical and cross-location analytics are not supported by the published policies without written confirmation. [Place Details](https://developers.google.com/maps/documentation/places/web-service/place-details) [Places policies](https://developers.google.com/maps/documentation/places/web-service/policies) [EEA Places permitted uses](https://cloud.google.com/terms/maps-platform/eea-places-api-permitted-uses)
- Conditional for future Wolt reviews: the optional `REVIEW` webhook could support reviews received after connection if Wolt enables it and provides the event/read schema and display rights. The canonical Wolt venue score, review history, and backfill remain blocked because no public read contract was found. Scraping remains unsupported. [Wolt webhook guide](https://developer.wolt.com/docs/webhook) [Wolt Denmark terms](https://explore.wolt.com/en/dnk/terms)

## Google supported paths

### Google Business Profile Reviews API

The GBP API is the correct owner-authorized source when the chain wants its own Business Profiles. The list method accepts a parent in the form `accounts/*/locations/*`, is valid only for a verified location, supports pagination up to 50 reviews per page, and returns `averageRating`, `totalReviewCount`, and the review list. [Reviews list reference](https://developers.google.com/my-business/reference/rest/v4/accounts.locations.reviews/list)

The review resource includes star rating, comment, creation and update timestamps, reviewer information, reply data, media fields, and an `isAnonymous` flag. For anonymous reviewers, the documented display name and profile photo fields are not populated. The product should preserve that distinction and must not infer an identity. [Review resource](https://developers.google.com/my-business/reference/rest/v4/accounts.locations.reviews)

Every request requires an OAuth 2.0 token with the broad `business.manage` scope. The reviewed documentation does not offer a review-only, read-only scope. Offline access is available through a refresh token, and the user can revoke authorization. The connection screen must explain that scope clearly, and the product must enforce read-only behavior itself. [OAuth overview](https://developers.google.com/my-business/content/oauth-overview) [OAuth implementation](https://developers.google.com/my-business/content/implement-oauth)

Google's OAuth guide expressly supports partner platforms acting for an owner after manual sign-in and consent, including offline actions. Its API policy separately prohibits giving clients indirect programmatic access through the platform's approved project and requires end users to sign in manually. A dashboard that renders data for a signed-in, authorized user is different from exposing a proxy API or customer-run script, but Google should confirm the planned background-refresh flow during project approval. [OAuth implementation](https://developers.google.com/my-business/content/implement-oauth) [GBP API policies](https://developers.google.com/my-business/content/policies)

Google does not make GBP API access public by default. The applicant must request API access for a Cloud project, and the published prerequisites include managing a verified, active Business Profile for at least 60 days, having a business website, and applying with an owner or manager email. A user's authorization still grants access only to the profiles that user can access. [API prerequisites](https://developers.google.com/my-business/content/prereqs) [GBP API FAQ](https://developers.google.com/my-business/content/faq)

Google's pricing page currently describes registered Google My Business API users as having no charge. Quotas still apply, and the limits page documents quota errors and default per-minute quotas for the API families. The reviewed quota pages do not publish a separate review-specific quota, so the implementation must monitor the assigned project quota rather than assume unlimited review polling. [Google My Business API pricing](https://developers.google.com/my-business/content/pricing) [API limits](https://developers.google.com/my-business/content/limits)

The location mapping must be explicit. A GBP `LocationKey` can contain a `placeId` when the location is verified, connected, or appears on Maps, but it can be empty for locations created outside the API. A `storeCode` is unique only inside its GBP account. Maps place IDs can change and are not guaranteed to be permanent, so do not map a restaurant solely by name or address. [Location resource](https://developers.google.com/my-business/reference/rest/v4/accounts.locations) [Locations setup](https://developers.google.com/my-business/content/locations-setup) [Place ID guide](https://developers.google.com/maps/documentation/places/web-service/place-id)

The Notifications API can publish `NEW_REVIEW` and `UPDATED_REVIEW` events through Cloud Pub/Sub. The event provides a review resource name and location name, after which the service should call the Reviews API. Google documents the trigger and setup, but not a delivery or freshness guarantee. [Notification setup](https://developers.google.com/my-business/content/notification-setup) [Notification setting reference](https://developers.google.com/my-business/reference/notifications/rest/v1/NotificationSetting)

The main product constraint is Google's GBP content policy. It says API content may not be prefetched, cached, indexed, or stored outside the permitted exceptions, limits temporary storage to no more than 30 calendar days, and prohibits manipulating or aggregating the content. It also requires the third-party relationship to be transparent and describes disconnect and access-removal obligations when a client leaves. [Google Business Profile API policies](https://developers.google.com/my-business/content/policies)

For this product, that means a long-lived Convex table of raw reviews, a review-history chart, or a chain-wide review aggregate needs Google's confirmation before launch. A short-lived, tenant-scoped cache used to render the authorized location view may be possible under the policy, but the exact implementation and retention should be reviewed with Google and counsel. That is a compliance interpretation, not a new Google permission.

### Google Maps Platform Places API (New)

Places Place Details is a public lookup keyed by a Google `place_id`. The Place resource defines `rating` as a 1.0 to 5.0 user-review rating and `userRatingCount` as the number of reviews with or without text. Place Details can also return `reviews`, but the documented maximum is five and the default order is relevance. [Place resource](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places) [Place Details](https://developers.google.com/maps/documentation/places/web-service/place-details)

This is not the same source contract as GBP. GBP exposes an authorized profile's `averageRating`, `totalReviewCount`, and paginated review set, while Places exposes public Place fields and only a five-review sample. The documentation does not promise that the two aggregates are identical. The UI should label the provider source and never silently combine their values. [GBP Reviews API](https://developers.google.com/my-business/reference/rest/v4/accounts.locations.reviews/list) [Places resource](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places)

Places requests require a field mask. `rating` and `userRatingCount` are Enterprise fields, and `reviews` is an Enterprise plus Atmosphere field, so requesting reviews can use a higher-priced SKU. The service also applies per-method, per-project per-minute rate limits. Current prices and free monthly billable-event allowances are category and region dependent; use Google's current pricing pages and do not hard-code a historical amount in product logic. [Places data fields](https://developers.google.com/maps/documentation/places/web-service/data-fields) [SKU details](https://developers.google.com/maps/billing-and-pricing/sku-details) [Usage and billing](https://developers.google.com/maps/documentation/places/web-service/usage-and-billing) [Pricing categories](https://developers.google.com/maps/billing-and-pricing/pricing-categories)

Places policies require a public Terms of Use and Privacy Policy that incorporate Google's terms, prohibit scraping and storage beyond documented exceptions, and require review-author attribution and Google Maps access. The review response includes attribution information and a `googleMapsUri`; the UI should show the author attribution and a direct source link when reviews are displayed. [Places policies](https://developers.google.com/maps/documentation/places/web-service/policies) [Place Details](https://developers.google.com/maps/documentation/places/web-service/place-details)

The durable identifier exception is the `place_id`. Google says place IDs may be stored indefinitely, while Places content itself is subject to the service's caching and storage rules. Store the selected place ID and local mapping metadata, then request current content when needed. [Place ID guide](https://developers.google.com/maps/documentation/places/web-service/place-id) [Places policies](https://developers.google.com/maps/documentation/places/web-service/policies)

Denmark falls under the Google Maps Platform EEA terms for EEA billing accounts. The Places permitted-use list includes displaying information about a customer's physical stores, but this product is a shared white-label SaaS displaying its customers' restaurants. The published wording does not clearly establish that those client restaurants count as the Google Maps customer's own stores. This is a material contract ambiguity, not a technical detail. Do not ship the Places fallback unless Google confirms the intended billing project, tenancy model, and dashboard display in writing. [EEA Places changes](https://developers.google.com/maps/comms/eea/places) [EEA Places permitted uses](https://cloud.google.com/terms/maps-platform/eea-places-api-permitted-uses) [EEA service terms](https://cloud.google.com/terms/maps-platform/eea/maps-service-terms)

## Wolt supported paths and gap

Wolt's public developer catalog describes Marketplace integrations for orders, venues, menus, assortment, and related operational flows. The Venue API covers operational venue data such as status, opening times, delivery configuration, and order-related status, not a ratings or review resource. The webhook guide separately lists an optional `REVIEW` notification tied to a consumer's order review or rating. [Wolt developer documentation](https://developer.wolt.com/docs) [Venue API](https://developer.wolt.com/docs/api/venue) [Webhook guide](https://developer.wolt.com/docs/webhook)

The webhook page's example is an order notification, and its documented follow-up is fetching an order payload. The public Order API reference reviewed does not define rating or written-review fields in that payload. The event is therefore useful as a possible trigger, but it is not by itself a canonical score or review read API. [Webhook guide](https://developer.wolt.com/docs/webhook) [Order API](https://developer.wolt.com/docs/api/order)

The restaurant integration guide describes OAuth 2.0 onboarding and access to Wolt APIs for a restaurant's operational integration. Wolt's authentication guide says an access token is short-lived, a refresh token is rotated and must be stored, and the token carries venue/resource context. None of those pages grants access to ratings or reviews. [Restaurant integration](https://developer.wolt.com/docs/getting-started/restaurant) [OAuth 2.0](https://developer.wolt.com/docs/authentication20)

Wolt's developer FAQ says its APIs are free to use, but a standard contract is required before environment access is shared. It documents rate limits per endpoint for Item, Inventory, and Menu APIs, not a review-specific quota or service level. [Wolt developer FAQ](https://developer.wolt.com/docs/faq)

Wolt's public Denmark Merchant Portal guide is evidence of a merchant-facing feature, not an API contract. It says customers rate the experience on a 1-to-10 scale, can leave a numeric rating and written review, and merchants can see recent reviews in Merchant Portal. [Merchant Portal rating guide](https://merchant.wolt.com/en/dnk/learning-center/how-to-improve-your-venue-rating-on-wolt)

Wolt's Denmark consumer terms describe a different part of the rating semantics: only users who purchased can rate, the venue average uses the preceding six months, the overall food or product rating affects the venue average, and Wolt updates the venue rating regularly. The terms do not state the 1-to-10 scale on that page. Treat the scale, field definitions, and window as Wolt-confirmation items rather than merging the two public descriptions into an assumed API schema. [Wolt Denmark terms](https://explore.wolt.com/en/dnk/terms) [Merchant Portal rating guide](https://merchant.wolt.com/en/dnk/learning-center/how-to-improve-your-venue-rating-on-wolt)

As of the date above, I found no documented public Wolt API read endpoint for venue score, review count, or complete written-review export in the developer catalog, Venue API, or Order API. The optional `REVIEW` webhook is a plausible supported trigger for future per-order reviews, but the public documentation does not say what it contains or how the review is read. Wolt must enable the event and provide the exact contract before implementation. If it only delivers events after connection, a locally calculated value must be labeled as a period rating, such as "since connected," and must not be presented as Wolt's canonical six-month venue score. This is a documentation finding, not proof that Wolt has no private or commercial interface. [Wolt developer documentation](https://developer.wolt.com/docs) [Venue API](https://developer.wolt.com/docs/api/venue) [Order API](https://developer.wolt.com/docs/api/order) [Webhook guide](https://developer.wolt.com/docs/webhook)

The public storefront is not an alternative. Wolt's Denmark terms prohibit collecting, using, copying, or transferring information obtained from the service without Wolt's consent, prohibit bots and automated methods, and say users may access the service only through expressly provided interfaces. Do not use browser automation, reverse-engineered JSON calls, or an undocumented endpoint as a product integration. [Wolt Denmark terms](https://explore.wolt.com/en/dnk/terms)

### Recommended vendor path

If the goal is to outsource Google onboarding and review normalization, run a short commercial validation with ReviewTrackers and Uberall. ReviewTrackers has the clearest public data-only and custom-application story. Uberall has the clearest full partner, provisioning, and white-label account model. Use Yext as the enterprise comparison and keep Birdeye as an optional fourth quote if price pressure matters.

Do not buy any of them on the assumption that Wolt is included. Require the vendor to show a current production Wolt payload, name the source interface, and provide written Wolt redistribution permission. A statement that the vendor "integrates with Wolt" is insufficient because Wolt's published partner program is primarily for orders, menus, inventory, and venue operations.

The smallest likely outcome remains direct GBP for Google plus a separate Wolt commercial agreement. A reputation vendor adds another tenant model, location mapping, DPA, contract, and per-location cost while leaving the Wolt gap open.

### Procurement gates

Before a trial or contract, require written answers to these points:

1. Does Google data come from each merchant's authorized GBP connection, or from page scraping? Require the authorized GBP route.
2. Is Wolt review access real? Ask for the production schema, canonical venue score, review count, written review fields, backfill, edit and deletion events, and venue-ID mapping.
3. Does the license allow API retrieval, temporary Convex caching, white-label display to tenant users, provider attribution, derivative aggregates, and deletion on disconnect?
4. Which publishers are excluded from API export even when visible in the vendor UI?
5. What are the per-location price, minimum annual commitment, sandbox access, quota, freshness target, support SLA, export rights, and termination process?
6. What DPA, EEA hosting or transfer terms, subprocessors, reviewer-PII handling, and tenant-isolation controls apply?
7. Who bears liability if Google or Wolt withdraws access? Vendor indemnity must cover the planned Denmark and EEA use, not only the act of scraping in a US court.

A trial should start only after those document checks. A technically successful scrape is not evidence that the product may lawfully store and show the data.

## Fit with the existing application

The existing Wolt integration already has most of the operational plumbing a future supported review flow would need. Its tables map a Wolt venue to an organization and local location, keep encrypted OAuth credentials, and store connection state. Its signed webhook route and order-fetch flow already receive Wolt events. [Wolt integration tables](../convex/schema.ts) [Wolt API parser](../convex/lib/woltApi.ts) [Wolt operations](wolt-operations.md)

The current parser only retains order, venue, status, time, and sales data. The public Order API shape used by the app has no review or rating fields. A `REVIEW` event would therefore be ignored or reduced to the existing event fields today. Once Wolt supplies a supported schema, the smallest implementation should extend this adapter and reuse the existing venue mapping. It should not add a second Wolt connection.

The dashboard's current metric contract is numeric and time-series based. It supports units such as count, currency, percent, quantity, and hours, with optional numeric breakdown rows. It cannot correctly represent review text, author attribution, provider links, moderation state, or deletion. [Dashboard metric types](../lib/dashboard/types.ts)

The smallest useful dashboard change is therefore two separate, generic concepts:

1. A current per-location score card with an explicit provider scale or maximum. It should show Google and Wolt side by side, not combine them. Google is on a 5-point scale; Wolt's merchant material describes a 10-point scale and its displayed venue score uses a rolling six-month window.
2. A generic review feed or separate reviews view for individual text. Do not encode comments inside numeric breakdown labels or add provider-specific widget UI.

The score card also needs snapshot semantics. A provider's current score should not pretend to follow the dashboard's selected date range, and the application must not manufacture a historical series from short-lived cached snapshots. It should show the provider-returned per-location aggregate and its "as of" time. Do not calculate a chain-wide Google score or a cross-platform composite unless the providers expressly permit it and the product defines a valid weighting rule.

## Legal and operational constraints

This assessment does not establish legal compliance in Denmark or any other jurisdiction. The launch gate is provider permission plus a privacy and contract review for each organization's use case.

### Google Business Profile

- Use only profiles and locations for which the merchant has authorized access. Google says the API may be used for listings the user owns or is authorized to manage, and a third-party relationship must be transparent. [GBP API policies](https://developers.google.com/my-business/content/policies)
- Require the administrator's interactive Google sign-in and do not expose Business Profile data through a customer-callable proxy API or automation interface. Include any unattended refresh schedule in the API-access application so Google can confirm that it is the platform acting on the owner's consent. [OAuth implementation](https://developers.google.com/my-business/content/implement-oauth) [GBP API policies](https://developers.google.com/my-business/content/policies)
- Treat review text, reviewer fields, media, and replies as provider content. Do not build an indefinite raw-review archive or derive chain-wide analytics from stored GBP content unless Google confirms that the intended use is allowed. The published policy expressly addresses temporary storage and aggregation. [GBP API policies](https://developers.google.com/my-business/content/policies)
- Preserve `isAnonymous`; do not expose a profile photo or display name when the API marks the review anonymous. [Review resource](https://developers.google.com/my-business/reference/rest/v4/accounts.locations.reviews)
- Disconnect cleanly. Google describes easy disassociation and access-removal obligations after a client ends the third-party relationship. Revoke tokens, stop notifications, and delete provider content on the approved retention schedule. [GBP API policies](https://developers.google.com/my-business/content/policies)
- Use least-privilege product behavior. The same API family also permits replies and reply deletion, but this dashboard request needs read-only review access. Do not add reply automation without the user's specific express consent, which Google's policy requires for automated review replies. [GBP API policies](https://developers.google.com/my-business/content/policies)

### Google Places

- Show Google-required author attribution and a way to open the individual source review in Google Maps. Follow Google's guidance on review ordering, relative dates, translation notices, and average-rating notices where applicable. [Places policies](https://developers.google.com/maps/documentation/places/web-service/policies)
- Request only the fields needed for the screen. `reviews` increases the billing category, and field masks control both response shape and cost. [Places data fields](https://developers.google.com/maps/documentation/places/web-service/data-fields) [SKU details](https://developers.google.com/maps/billing-and-pricing/sku-details)
- Do not treat Places content as a synchronized source for Convex history. Keep `place_id` and local mapping metadata; use an ephemeral response cache only where Google's current policy permits it. [Places policies](https://developers.google.com/maps/documentation/places/web-service/policies) [Place ID guide](https://developers.google.com/maps/documentation/places/web-service/place-id)
- Provide the application's Terms of Use and Privacy Policy with the required Google terms and privacy disclosures. [Places policies](https://developers.google.com/maps/documentation/places/web-service/policies)

### Wolt

- Merchant Portal visibility does not equal an export license or API entitlement. Obtain the Danish merchant agreement, applicable Marketplace/API addendum, and a written statement of what may be copied into a tenant dashboard. [Wolt Merchant Portal](https://merchant.wolt.com/en/dnk) [Wolt Denmark terms](https://explore.wolt.com/en/dnk/terms)
- Treat written reviews as potentially personal and user-generated data. The public Wolt pages reviewed do not specify the API fields, reviewer identity rules, deletion events, retention period, controller/processor allocation for a third-party dashboard, or cross-location display rights. These remain open contractual and privacy questions. [Wolt Denmark privacy statement](https://explore.wolt.com/en/dnk/privacy) [Wolt Denmark terms](https://explore.wolt.com/en/dnk/terms)
- Do not infer a supported integration from network traffic in `wolt.com`, from a portal session, or from a third-party library. Use only the documented webhook plus read flow, or another Wolt-documented or expressly contracted interface. [Wolt developer FAQ](https://developer.wolt.com/docs/faq) [Wolt webhook guide](https://developer.wolt.com/docs/webhook) [Wolt Denmark terms](https://explore.wolt.com/en/dnk/terms)

### Multi-tenant operation

The SaaS should map each local `Lokation` to an explicitly authorized provider account and venue/location identifier. Keep that mapping and consent metadata tenant-scoped, never match locations by name alone, and never expose one chain's provider content to another chain. Google requires location-level user access, and Wolt's documented OAuth flow carries venue context. [Google location resource](https://developers.google.com/my-business/reference/rest/v4/accounts.locations) [Wolt OAuth 2.0](https://developer.wolt.com/docs/authentication20)

Because the application's normal pattern is to synchronize external data into Convex, provider storage rules matter before schema design. The safe default is to synchronize only provider identifiers, consent state, last-attempt metadata, and short-lived content permitted by the provider. Do not create a durable, provider-agnostic review history or dashboard metric from Google or Wolt content until the corresponding provider has approved that use.

## Recommended product approach

### Phase 0: access and contract gate

1. **Google GBP, conditional go after approval.** Request GBP API access, configure OAuth with `business.manage`, and have each chain administrator authorize the specific GBP account and locations. Record the provider account and location resource IDs, plus a selected Maps `place_id` where useful. [GBP prerequisites](https://developers.google.com/my-business/content/prereqs) [OAuth implementation](https://developers.google.com/my-business/content/implement-oauth) [Location resource](https://developers.google.com/my-business/reference/rest/v4/accounts.locations)
2. **Google, conditional for persistence.** Ask Google or qualified counsel to approve the intended Convex retention, review-history behavior, and any chain-level rollup. The published policy is not a safe basis for assuming that raw review storage or aggregation is allowed. [GBP API policies](https://developers.google.com/my-business/content/policies)
3. **Google Places, do not ship by default.** Ask Google whether the shared white-label tenancy model is a permitted EEA Places use. Without written confirmation, do not use it as a fallback. [EEA Places permitted uses](https://cloud.google.com/terms/maps-platform/eea-places-api-permitted-uses)
4. **Wolt, blocked pending confirmation.** Ask Wolt for the review event and read schema, canonical score endpoint or export, history/backfill, scopes, rate limits, deletion behavior, and written permission to display the result in this SaaS. Until that exists, do not promise a canonical Wolt score, backfill, or complete review inbox. [Wolt developer FAQ](https://developer.wolt.com/docs/faq) [Wolt webhook guide](https://developer.wolt.com/docs/webhook)

### Phase 1: Google Business Profile live view

Use the Reviews API for the authorized location. Start with a daily and on-demand Convex action refresh plus periodic full reconciliation. That fits the application's existing backend and avoids adding Google Cloud Pub/Sub solely for a dashboard snapshot. If the product later requires near-real-time updates, Pub/Sub can signal `NEW_REVIEW` and `UPDATED_REVIEW`, after which the app fetches the changed resource; Google does not publish a freshness SLA or a complete deletion-event contract. [Notification setup](https://developers.google.com/my-business/content/notification-setup) [Reviews list](https://developers.google.com/my-business/reference/rest/v4/accounts.locations.reviews/list)

Render the provider-returned `averageRating` and `totalReviewCount` per location, and show individual reviews only with the documented anonymity and attribution behavior. Keep content in a short-lived, encrypted, tenant-scoped cache while the Google policy review is pending. Provide a source link to the location's Google review surface where appropriate. [Review resource](https://developers.google.com/my-business/reference/rest/v4/accounts.locations.reviews) [Locations setup](https://developers.google.com/my-business/content/locations-setup) [GBP API policies](https://developers.google.com/my-business/content/policies)

### Phase 2: Places only after written approval

Do not treat Places as the automatic fallback when a chain cannot complete GBP authorization. First obtain Google's written confirmation that this EEA-billed, shared white-label SaaS is a permitted use. If approved, expose it only as a clearly labeled request-time public snapshot. Resolve a user-confirmed `place_id`, request only the necessary fields, and display no more than the documented five reviews with author attribution and Google Maps access. [Place Details](https://developers.google.com/maps/documentation/places/web-service/place-details) [Places policies](https://developers.google.com/maps/documentation/places/web-service/policies) [EEA Places permitted uses](https://cloud.google.com/terms/maps-platform/eea-places-api-permitted-uses)

Do not use Places to populate historical score changes, a complete review inbox, or a chain-wide review metric. Its review sample, public-place semantics, billing, and content-storage rules make that an inappropriate substitute for GBP owner access. This is a product recommendation based on the two documented contracts. [Places resource](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places) [GBP Reviews API](https://developers.google.com/my-business/reference/rest/v4/accounts.locations.reviews/list)

### Phase 3: Wolt decision

Until Wolt documents the payload and read path behind its optional `REVIEW` signal, provide a manual link or workflow for an authorized merchant to open Merchant Portal and inspect Wolt reviews. Do not copy the review text into the SaaS from the browser and do not present a Wolt score as an automatically synchronized dashboard metric. [Wolt webhook guide](https://developer.wolt.com/docs/webhook) [Wolt Merchant Portal](https://merchant.wolt.com/en/dnk) [Wolt Denmark terms](https://explore.wolt.com/en/dnk/terms)

If Wolt confirms the optional event-and-read flow, extend the existing Wolt adapter with explicit per-venue authorization, documented field and scale handling, deletion and retention rules, attribution requirements, and tenant-scoped sync. If Wolt provides only future events, label the result by its actual collection period and do not call it Wolt's venue score. A canonical score requires Wolt's own score endpoint or export. Do not reuse Google assumptions for Wolt's rating window or review ownership.

### Phase 4: operations and offboarding

Monitor Google quota responses and back off on rate-limit errors. Keep provider identifiers separate from application location IDs, handle place-ID changes, and tolerate additive provider fields. On disconnect, revoke or discard credentials, stop notification delivery, remove cached provider content under the approved retention policy, and preserve only the minimum audit record needed by the application's own security and billing obligations. [GBP API limits](https://developers.google.com/my-business/content/limits) [Place ID guide](https://developers.google.com/maps/documentation/places/web-service/place-id) [GBP API policies](https://developers.google.com/my-business/content/policies) [Wolt OAuth 2.0](https://developer.wolt.com/docs/authentication20)
