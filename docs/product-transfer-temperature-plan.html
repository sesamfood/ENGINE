Implementation plan

Product maximum temperatures in transfers

Add optional temperature tracking to products, require a blank-by-default measurement for tracked products during transfers, flag deviations with a yellow exclamation mark, and retain an auditable snapshot without turning deviations into a separate workflow.

Decision complete Prepared 20 August 2026 Target: current Next.js and Convex application

Summary

Outcome. A product may define a maximum transfer temperature in degrees Celsius. A transfer records one temperature per distinct product, even when that product has several unit lines. Tracked products require a measurement. Untracked products accept one optionally. An over-limit value requires the existing transfer comment and one explicit confirmation.

One measurement per product

Cases, units, and other quantity lines share the same measured value.

Celsius with one decimal

Allow values from -100.0 through 100.0 °C, including negative temperatures.

Historical limits stay fixed

Each transfer keeps the maximum that applied when the product was added.

Deviations can be recorded

A comment and confirmation are required. The system does not reject the real measurement.

Old transfers are grandfathered

Existing products retain their captured rule. Newly added products use current settings.

Deviations stay visible

A yellow exclamation marks affected products during entry and affected rows in transfer history.

Data model and contracts

Product settingOptional maximum in °C. Empty means temperature tracking is off.
→
Transfer entryOne product measurement. Server checks requirement, deviation, comment, and confirmation.
→
Historical snapshotRecorded temperature and applicable maximum feed detail view and CSV export.

Stored fields

Add optional numeric fields so existing Convex documents remain valid and no backfill is required.

products.maxTemperatureCelsius?: number

transferItems.temperatureCelsius?: number
transferItems.maxTemperatureCelsius?: number

The mutation accepts one measurement per distinct product. The server copies the canonical measurement and captured maximum to every transferItems row for that product. This matches the existing item-level snapshot and export model without adding another table. Do not store a separate deviation boolean because temperatureCelsius > maxTemperatureCelsius derives it.

History summary contract

TransferHeader.hasTemperatureDeviation: boolean

Derive this value while hydrateTransferHeader already has the transfer items for quantity totals. It is true when any item has both snapshot values and its measured temperature exceeds its captured maximum. Do not persist the summary or add another query.

Mutation input

productTemperatures?: Array<{
  productId: Id<"products">
  temperatureCelsius: number
}>

confirmedTemperatureDeviations?: Array<{
  productId: Id<"products">
  maxTemperatureCelsius: number
}>

Keep both arrays optional at the API boundary so old callers continue to work for untracked products. The server rejects duplicate product entries, measurements for products absent from the transfer, missing measurements for tracked products, invalid precision or range, and stale deviation confirmations.

Product mutation compatibility

Accept maxTemperatureCelsius?: number | null when creating, updating, or importing products. Omitted means untracked on create and preserve the current setting on update. null explicitly clears the setting. A number sets it after server validation.

Implementation sequence

1. Widen the catalog and transfer schemas

GoalPersist optional product limits and immutable transfer snapshots without migrating old rows.

ChangeAdd the optional fields in convex/schema.ts. Extend catalog and transfer validators, return values, and hydration in convex/catalog.ts and convex/transfers.ts.

RulesValidate finite values, one decimal at most, and the inclusive -100.0 to 100.0 °C range on the server. Exactly the configured maximum is compliant.

SecurityRetain organization checks and existing permissions. Catalog changes use catalog.manage; capture and edits use transfers.manage; history and export keep their current view/export permissions.

2. Add the optional product setting

GoalLet catalog managers enable tracking by entering one maximum value.

ChangeAdd a blank optional number field to the product details section in components/catalog/product-form.tsx. Use the existing Field, Input, and question-mark help tooltip patterns. Do not add a separate switch.

BehaviorUse decimal input with a °C suffix, preserve an empty string as “not tracked,” parse only on submit, and send null when a manager clears an existing value. Keep all new interface copy in Danish.

FeedbackShow the range or precision error at the field. Keep existing save success and failure feedback.

3. Capture and validate transfer temperatures

GoalCollect one blank-by-default temperature for each distinct product and prevent unconfirmed deviations.

ChangeReturn the current maximum from getTransferProductOption. In components/transfers/transfer-form.tsx, place one temperature field in each product group rather than each unit row. Adding another unit preserves the product measurement; removing the last unit removes it.

RequiredA product with a captured maximum must have a measurement. A product without one may leave the field empty or record a value. No new product receives a temperature default.

DeviationMark an over-limit product immediately with a yellow TriangleAlertIcon beside its product name and temperature field. Pair the icon with visually hidden text that says the product has a temperature deviation, and keep the numeric explanation visible at the field so color is not the only signal.

ConfirmIf deviations remain when saving, require the existing transfer comment, then open one shadcn AlertDialog listing every affected product with measured and maximum values. The confirm action resubmits the exact acknowledged product and maximum pairs.

ServerDerive all requirements from organization-scoped product rows or stored snapshots. Never trust client-provided limits. Reject a confirmation when its maximum no longer matches, so the UI must refresh and show the changed rule before asking again.

4. Preserve edit semantics

GoalA historical transfer must not change compliance because someone later edits a product setting.

ExistingFor product IDs already present on the transfer, use the stored maximum and load the stored measurement. Legacy rows with no captured maximum stay untracked, even if the catalog product now has a maximum.

NewFor a product ID newly added during an edit, use its current catalog maximum and apply the same measurement and deviation rules as creation.

SaveContinue the current atomic delete-and-reinsert item update, but carry the canonical product measurement and captured maximum onto every replacement line.

5. Expose warnings, history, and export data

DetailExtend transfer detail rows with nullable measured and maximum temperatures. Display one temperature summary per product group and a clear deviation treatment when the measured value is above the captured maximum.

History rowAdd hasTemperatureDeviation to the transfer header result. In the existing table, show a yellow TriangleAlertIcon immediately before the timestamp when the value is true. Keep the current columns and row layout. Add a concise tooltip, visually hidden text, and "with temperature deviation" to the clickable row's accessible label.

CSVAdd selectable “temperature,” “maximum temperature,” and “temperature deviation” columns through the existing export column system. Return the item snapshot from exportTransfers. Preserve saved column preferences; fresh preferences include the new columns with the existing defaults.

UnchangedDo not add a separate status column, history filter, dashboard metric, stock calculation, or transfer total.

6. Keep product archives compatible

GoalMove the setting with product data without letting a legacy archive erase data it could not represent.

FormatUpdate lib/product-archive.ts so new exports write archive version 2 and always include maxTemperatureCelsius as a number or null. Continue accepting version 1.

ImportA version 1 product creates as untracked. When it overwrites an existing product, preserve that product’s maximum. Version 2 null clears the maximum and a number replaces it. Thread the value through the current product import flow.

Acceptance and verification

Repository rule. Do not add new automated tests unless the user asks for them. Update existing fixtures only if an interface change makes that necessary. Verify with the existing checks and the manual scenarios below.

ScenarioExpected result
Product maximum left emptyPass Product saves as untracked; its transfer temperature stays optional and empty by default.
Tracked product has no measurementPass Client shows an inline error and the server rejects the save.
Measurement equals maximumPass Transfer saves without deviation confirmation.
Measurement exceeds maximumPass Empty comment blocks progress; a comment opens the deviation dialog; explicit confirmation saves.

Legacy transfer is editedPass Existing products remain grandfathered; a newly added tracked product requires a blank new measurement.
Stale confirmation is submittedPass Server rejects it and the user must review the current maximum.
History contains a deviationPass Its table row has a yellow exclamation before the timestamp; compliant and legacy rows do not.

Explicit boundaries

  • No minimum temperature, arrival temperature, per-unit-line temperature, or automatic sensor integration.
  • No separate deviation entity, reason per product, remediation workflow, notification, dashboard metric, status column, or history filter.
  • No new role or permission. Existing catalog, transfer, view, and export permissions remain authoritative.
  • No Convex backfill. Missing optional fields mean the historical product or transfer did not use temperature tracking.
  • No change to stock movement, product quantities, transfer totals, or provider integrations.

Domain documentation

Add the agreed terms to the root CONTEXT.md: Maximum transfer temperature, Transfer temperature, and Temperature deviation. No ADR is needed. The decisions are feature-local, follow the existing transfer snapshot model, and can change without replacing an architectural boundary.
