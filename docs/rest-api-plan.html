Implementation plan

Public REST API

Add a versioned, publicly supported API for external server-to-server integrations. Better Auth owns organization API keys. Convex remains the authority for tenant scope, permissions, location access, validation, and domain rules.

Decision complete Prepared 23 August 2026 Target: Next.js 16, Better Auth, Convex, and Vercel

Outcome

Ship /api/v1 as a thin HTTP adapter. A client sends an organization-owned API key. Better Auth verifies the credential. The route exchanges that verified identity for a short-lived service-principal token used only for the Convex call. Convex then loads the key policy and applies the same permission and location rules used by the application.

Server-to-server clients

Every API key belongs to exactly one Better Auth organization. The API never accepts a caller-selected organization as authority.

CRUD where the domain permits it

Normal resources use standard methods. Workflow records keep named commands, locks, audit reasons, archive rules, and immutable history.

Public contract from day one

The URL starts at /api/v1. OpenAPI 3.1, hosted English documentation, request examples, and a changelog ship with the first endpoints.

API keys first

Use Better Auth organization API keys for v1. Add OAuth client credentials only after a partner requires OAuth interoperability.

Existing access rules stay authoritative

Each key receives an existing role profile, a subset of that role's app permission IDs, and an optional location scope. Client-side hiding never replaces a Convex check.

Staged delivery

Build one common contract, release low-risk master data first, then add operational domains after retry and state-transition safeguards exist.

No webhooks or SDKs in v1

Clients use cursor pagination and supported updated-time filters. Usage will decide later webhook events and SDK languages.

Public support without an initial SLA

Publish incidents and a support route. Track a 99.9% monthly internal availability target. Use test organizations in a non-production deployment instead of a separate sandbox product.

Stop gate. The lockfile installs better-auth 1.6.15 and @convex-dev/better-auth 0.12.5. The adapter declares a Better Auth peer range of >=1.6.11 <1.7.0, while the manifest uses a caret range. The app does not contain @better-auth/api-key, and the generated Better Auth schema has no API-key table. Work package 0 must freeze and prove an exact supported version set before production schema changes. If organization-key verification and a non-human Convex principal cannot work together, stop and choose a coordinated dependency upgrade. Do not create synthetic human users as a shortcut.

Principal model

Replace the human-shaped OrganizationAuth contract with one normalized authorization envelope and a discriminated actor. Common guards can use the common fields. Human-only code must narrow the principal first. 

type AuthorizationContext = {
  organizationId: string;
  role: OrganizationRole;
  granularity: DataGranularity;
  permissions: ReadonlySet<PermissionId>;
  locationScope: {
    all: boolean;
    ids: ReadonlySet<Id<"locations">>;
  };
  tokenIdentifier: string;
  principal:
    | {
        kind: "user";
        userId: string;
        sessionId: string;
        name: string;
        isKioskAccount: boolean;
        kioskModeEnabled: boolean;
        kioskLocationId: Id<"locations"> | null;
      }
    | {
        kind: "apiKey";
        apiKeyId: string;
        name: string;
      };
};

Choose the union branch from the allowlisted JWT issuer, then validate all custom claims before constructing the context. Do not branch only on a free-form kind claim or cast unknown claims. Add a requireHumanPrincipal guard for code that needs a user, session, kiosk state, password confirmation, or a named employee. Never fill those fields with API-key placeholders.

Make both Convex paths return this contract. Queries and mutations resolve it directly. Actions currently round-trip through internal.access.getRoleContext, whose validator and implementation assume a human session; update that path to resolve and serialize either principal kind. Audit every consumer of userId, sessionId, userIdentifier, userName, and kiosk fields before changing the type. The signed service token carries identity, not authoritative permissions. Convex loads current API-key policy on every call, so revocation, expiry, role changes, permission changes, and location changes apply on the next public request.

Credential transport

Accept the raw key only as Authorization: Bearer <api-key>. Reject query-string credentials, duplicate authorization headers, and other schemes. Better Auth's API-key plugin defaults to x-api-key. Either configure its customAPIKeyGetter to parse this exact Bearer contract or let the route parse it and call the plugin's supported server-side verifyApiKey API. Do not accidentally publish the default header as a second contract. After verification, remove the raw key from downstream headers and create a service token with a maximum lifetime of 30 seconds.

Keep the existing Better Auth Convex provider with applicationID: "convex". Add a second custom JWT provider with the distinct applicationID: "rest-api-v1", a dedicated issuer and audience, RS256, and the public key URL /.well-known/rest-api-jwks.json. The installed adapter filters its own provider by the convex application ID and rejects duplicates, so work package 0 must prove that both providers coexist. Never assign the service provider that application ID. Store private signing keys only in Next.js deployment secrets. The JWKS route is unauthenticated, returns public JWKs only, has an explicit public cache policy, and supports overlapping keys during rotation. The public client never receives the service token. Do not add a public Convex function that returns one.

Use a request-local ConvexHttpClient, call setAuth with the service token, and invoke generated function references. Do not reuse fetchAuthQuery, fetchAuthMutation, or fetchAuthAction for API-key requests because those helpers obtain a human session token. Do not add a second public httpAction path as a fallback. If the lockfile-installed Convex deployment cannot accept the custom JWT provider, stop at work package 0 and resolve the dependency set.

Policy storage

Better Auth owns the hashed credential, owner reference, enabled state, expiry, rate-limit counters, and last request time. Add an organization-scoped Convex policy record keyed by the Better Auth API-key ID. Store an existing organization role key, an explicit subset of that role's app permission IDs, a required location policy, creator, and audit timestamps. Resolve data granularity and role-gated resources from the current role record. This preserves dashboard role audiences and similar checks that use role as well as permissions. 

type ApiKeyLocationAccess =
  | { scope: "all"; locationIds: [] }
  | {
      scope: "selected";
      locationIds: Id<"locations">[];
    }
  | {
      scope: "operator";
      operatorId: Id<"operators">;
      locationIds: [];
    };

The UI may present location access as optional, but the stored policy is never null or missing. An omitted selection is converted server-side to an explicit all policy after the creator's access is checked. A selected policy contains 1 to 200 unique organization-owned location IDs. An operator policy contains one organization-owned operator ID and resolves its locations through resolveStoredLocationScope. Detect more than the supported 200 locations and reject the policy instead of silently truncating it. Reject malformed or missing policies closed; never interpret them as all-location access.

The Convex policy is the single authority for application permissions. Do not mirror those permission IDs into Better Auth's optional per-key permission field. Better Auth's organization apiKey actions govern who may manage credentials, which is a separate rule. Use a separate location-access table only if the existing access query pattern needs indexed rows. Location access follows each domain's current rule. In particular, selected and operator scopes do not restrict Transfers today. Document and retain that exception unless a separate product change alters it.

At key creation, the selected role, permissions, and locations must all fit within the creator's current access. Effective key permissions are the intersection of the stored key grant and the role's current permissions. A later permission reduction therefore takes effect on the next request. Do not delete a custom role while an API key references it. A later change to the creator does not silently change the organization-owned key. An authorized administrator must edit or revoke it.

Public HTTP contract

Resource and command conventions

  • Use plural, English resource names below /api/v1.
  • Use GET for reads, POST for creation and commands, PATCH for partial updates, and DELETE only when the domain permits deletion or deactivation.
  • Use named command paths for state transitions, such as POST /api/v1/products/{productId}/archive and POST /api/v1/counts/{countId}/submit.
  • Reject unknown request fields. An omitted property means unchanged. null clears a property only when the contract says that the property is nullable.
  • Represent timestamps as UTC ISO 8601 strings. Represent money as integer minor units. Keep quantities and units in explicit fields.
  • Map a Convex document ID to the public id string and treat that value as stable for the resource's lifetime. Do not add a second global ID system. Every lookup validates the expected table, organization ownership, and permission before returning data. A foreign object ID returns 404.
  • Return English field names, enum values, documentation, and error text. Return stored Danish names and business content without translation.

Wrap successful data so collection metadata can grow without changing the resource schema. Return 204 No Content only when no response representation helps the caller.

Pagination, filters, and concurrency

Use opaque Convex-compatible cursors and bounded page sizes. Start with a default of 50 and a maximum of 100. Pass pagination options unchanged to Convex pagination. Each endpoint declares an allowlist of filters and sort fields. Support updatedAfter only after the resource has a reliable indexed update timestamp. Do not imply that this filter reports hard deletions. Without a durable change log, clients must periodically reconcile a complete paginated snapshot.

Expose an opaque version for resources that support concurrent edits. Require If-Match on risky updates and deletes. Return 412 Precondition Failed when the version is stale. Map existing revision contracts, such as dashboard expectedUpdatedAt, into this rule.

Return Cache-Control: private, no-store on authenticated organization data by default. Cache only public OpenAPI and documentation assets with an explicit policy. Do not let a CDN cache a response keyed only by URL when authorization changes its contents.

Errors

Return application/problem+json using RFC 9457. Keep code stable and machine-readable. Keep detail safe for support logs. Add field pointers for validation errors and a request ID for every failure. 

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json
X-Request-Id: req_opaque

{
  "type": "https://api.example.com/problems/validation-error",
  "title": "Request validation failed",
  "status": 422,
  "detail": "One or more fields are invalid.",
  "instance": "/api/v1/products",
  "code": "validation_error",
  "requestId": "req_opaque",
  "errors": [
    { "pointer": "/unitId", "code": "invalid_reference" }
  ]
}

Use 401 for a missing or invalid key, 403 for a known principal without the required operation permission, 404 for a missing or foreign object, 409 for a state or idempotency conflict, 412 for stale concurrency state, 422 for valid JSON that fails request validation, and 429 for a rate limit. Map a structured Convex domain code to each public problem type. Do not compare Danish error messages to choose an HTTP status. Treat an unrecognized domain error as a generic 500 with a request ID. Never return stack traces, raw Convex errors, provider payloads, or Better Auth records.

Idempotency

Require Idempotency-Key for every POST that creates a resource or runs a side-effecting command. Scope a record by organization ID, API-key ID, operation ID, and idempotency key. Store a canonical request hash, completion state, HTTP status, and response for 24 hours. The first mutation must claim the key in the same transaction as the business effect.

  • The same key and request hash return the stored response.
  • The same key with a different request hash returns 409 Conflict.
  • A concurrent request for an operation still in progress returns a documented conflict response with Retry-After.
  • Transfer, Waste, Staff food, and bad delivery creation remain private until this behavior covers their stock and scheduled side effects.

The IETF Idempotency-Key document is still a work in progress. Document the app's exact behavior in OpenAPI instead of claiming standards compliance.

Limits and browser access

Reject JSON bodies above 1 MB before parsing. Keep files on domain-specific upload flows. Start with configurable limits of 120 requests per minute for normal operations, 30 mutations per minute, and 5 expensive export or sync requests per minute. Confirm these values with load checks before launch. Use Better Auth's persistent per-key limit during credential verification and the existing Convex rate-limiter component for limits scoped by organization, API-key ID, and operation. Do not use process memory on Vercel. Return the documented limit, remaining count, reset time, and Retry-After on 429.

Do not enable permissive CORS. Server-to-server clients do not need it. If the hosted documentation gains a request console, allow only that known origin and the required methods and headers.

Credential lifecycle and administration

Management permission

Add apiKeys.manage to lib/auth-permissions.ts. Grant it to Administrator by default. Custom roles may receive it. Manager and Medlem do not receive it by default. Stored rolePermissions override role defaults today. Do not silently insert this new permission into an organization's explicit override. Report affected organizations before rollout and require an authorized role manager to grant it.

Enable the Better Auth plugin's apiKey actions so its endpoints can run, then guard create, list, read, update, disable, and delete paths with a Better Auth hook that loads the current human session's Convex permission context and requires apiKeys.manage. Follow the existing member-management middleware pattern in convex/auth.ts. Better Auth's static access control only opens the transport action; the Convex permission check is authoritative for built-in and custom roles. Key administration remains a human-session feature in v1, and apiKeys.manage is not a grantable API-key permission.

Self-service flow

  1. Add an API-key page under the existing Administration area. Use shadcn components and Danish interface text.
  2. Ask for a name, an expiry no later than one year, an existing role profile, a subset of its app permissions, and optional location access.
  3. Check that every grant is within the administrator's effective access.
  4. Create the Better Auth organization key and its Convex policy as one coordinated operation. If the second write fails, revoke the first result.
  5. Show the raw key once. Never return it from list or detail operations.
  6. List the key ID, prefix, name, creator, created time, expiry, last use, permissions, locations, and status.
  7. Rotate by creating a replacement before revoking the old key. Do not change a secret in place.

Audit and telemetry

Write durable audit records for key creation, policy changes, rotation, disablement, and revocation. Treat each API request as key use. Update Better Auth's last-request value and emit structured request telemetry. Do not write every read request into the durable organization audit table unless retention and volume have been designed for it.

Widen auditLog before machine writes: add actorKind and actorApiKeyId, make actorUserId temporarily optional, and keep actorName. Interpret legacy rows with an actorUserId and no kind as users, backfill actorKind: "user", then narrow the schema so every new row has exactly the ID required by its actor kind. Update recordAudit to accept only the union above. Do not place an API-key ID in actorUserId.

Each request log contains the request ID, API-key ID, organization ID, operation ID, outcome, status, latency, response size, and rate-limit result. Redact the raw key, authorization header, request bodies, signed upload URLs, and provider secrets.

Human-bound rules

An API key is not a Bruger. It cannot satisfy a rule that requires the same human, a different human, a password confirmation, or a personal session. Map each such operation deliberately. For example, expose manager voiding with an audit reason instead of "undo my Waste," and do not let a service principal satisfy second-person Own Check approval. Keep an operation private until the domain has a machine-safe rule.

Inventory domain fields such as createdBy, performedBy, responsibleUserId, and actorUserId before exposing each write. If the field means a human, reject a machine principal. If it records a generic creator, widen it to an explicit principal kind and ID before launch. Do not overload a user field with an API-key ID.

GoalOperate the public API without leaking credentials or learning about failures from customers.

ChangeAdd structured request telemetry, latency and error metrics by operation, rate-limit metrics, key-revocation audit, dashboards, and alerts. Track 99.9% monthly availability for valid API requests and a p95 latency target of 1.5 seconds for normal operations. Exclude documented asynchronous export and sync commands from the latency target. Add an incident publication process and a support channel that accepts request IDs.

EvidenceAn operator can trace a failed request by ID without seeing a raw key or sensitive body. Alerts detect elevated 5xx, latency, auth failures, and rate-limit pressure.

9. Roll out without a flag day

GoalKeep the application stable while public coverage grows.

SequenceDeploy the principal bridge with no public keys. Enable key administration for one test organization. Exercise Phase 1 in a non-production deployment. Enable one production pilot organization. Publish the Phase 1 contract. Add later operations only after their gates pass.

RollbackDisable public key verification or revoke pilot keys without changing human sessions. Keep route code deployable before navigation and documentation announce an endpoint. Never roll back a published response field or enum value inside v1.

SupportPublish incidents and contract changes. Do not promise a contractual uptime SLA until operations data supports one.

EvidenceThe pilot can rotate and revoke credentials, complete a full sync, retry safely, and obtain support using request IDs. Human application traffic remains unchanged.

Acceptance and verification

Test authorization gate. Repository instructions prohibit adding tests unless the user asks for them. A publicly supported contract should have automated contract and authorization checks. Before implementation adds those checks, obtain explicit approval. Until then, use the existing test suite and the manual scenarios below. Do not publicly launch without a repeatable contract check.

Scenario Expected result
No API key or a malformed key Pass The endpoint returns an English RFC 9457 401 response with a request ID. It never redirects to login or returns HTML.
Expired, disabled, or revoked key Pass The next request fails. Cached service tokens cannot outlive the documented few-second internal window.
Known object ID from another organization Pass The endpoint returns 404 and does not reveal whether the object exists.
Key lacks the operation permission Pass Convex rejects the operation with 403. Hiding an endpoint in documentation or UI is not the control.
Key requests a location outside its scope Pass Existing location rules reject or filter the request. Transfers remain organization-wide for a key with transfers.view or transfers.manage, matching the current explicit exception.
Administrator creates a broader key than their own access Pass The server rejects the role, permission, or location grant. Request fields cannot override organization, role, permissions, or location access.
A stored key policy has no location branch, malformed IDs, or too many selected locations Pass Convex rejects the request closed. It never defaults the key to all locations or truncates an operator result.
A referenced role loses permission or is deleted Pass A permission reduction shrinks the key on its next request. Role deletion is blocked until all referencing keys change role or are revoked.
An API key calls a member, invitation, account, password, session, or key-management action Pass No public REST operation forwards the call. Better Auth's route still requires an authorized human session.
Key secret is created and later listed Pass The secret appears only in the creation response. Later reads show safe metadata and prefix only.
Two identical retry-sensitive requests use one idempotency key Pass The API returns the original response and creates one domain effect.
An idempotency key is reused with different input Pass The endpoint returns a stable 409 problem and performs no second effect.
A stale resource version is patched Pass The endpoint returns 412 with the current recovery guidance.
Page size exceeds 100 or cursor is invalid Pass The endpoint rejects the request without an unbounded Convex read.
Request contains an unknown writable field Pass The endpoint returns 422. It does not pass the field to Convex or Better Auth.

Compatibility and change policy

  • Keep additive endpoints and optional response fields within v1 when clients are required to ignore unknown optional data. Mark each enum as closed or extensible in OpenAPI. A new value in a closed enum is a breaking change and belongs in v2.
  • Do not remove or rename a field, change its type or meaning, tighten a previously valid input, or change pagination semantics inside v1.
  • Put a breaking contract in /api/v2. Run v1 and v2 together for at least 12 months after the deprecation notice.
  • Send the RFC 9745 Deprecation header, RFC 8594 Sunset header, and a Link to migration documentation on affected responses.
  • Keep the changelog factual. Name the first affected date, the last supported date, the replacement operation, and any required client action.
  • Do not publish an SDK until client usage identifies a language worth maintaining. The OpenAPI document remains the language-neutral contract.

Explicit boundaries and remaining gates

  • No raw Convex table access, dynamic function dispatch, GraphQL layer, or duplicate database.
  • No synthetic Better Auth users or long-lived sessions for machines.
  • No public forwarding of organization keys to Better Auth member, invitation, account, password, session, or API-key administration endpoints. Those remain human-session operations in v1.
  • No caller-selected organization, role, permission, actor, or unrestricted location claim.
  • No generic hard delete for records that the app archives, voids, reverses, versions, locks, or retains for audit.
  • No create, update, or delete API for provider-owned sales, employees, or schedules.
  • No raw OnlinePOS or Workfeed responses, provider secrets, Better Auth tables, internal sync functions, or arbitrary storage IDs.
  • No server-side fetch to a caller-supplied URL. Provider endpoints remain fixed by trusted integration configuration.
  • No generic file API. Each owning domain controls upload, validation, attachment, access, and cleanup.
  • No public audit-log read until a bounded, indexed, organization-scoped admin query exists.
  • No public dashboard-share reader in the organization API-key contract without a separate share-token design.
  • No webhooks, OAuth client credentials, generated SDKs, dedicated sandbox service, or contractual uptime SLA in v1.

Engineering gates remain, product decisions do not. Work package 0 must prove the dependency set and service-principal transport. Production Vercel limits must be measured. Automated contract and security checks need explicit user authorization under the repository rules. These gates may stop a release, but they do not reopen the API audience, scope, credential, language, support, or compatibility decisions.
