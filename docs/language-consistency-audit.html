The app speaks two vocabularies

The main navigation uses English product-area names. The work screens, permissions, kiosk setup, dashboards, exports, and server messages mostly use Danish. The result is not a handful of typos. Five core concepts change name as a user moves through the app.

What matters first

Decide the names for Transfer, Waste, Count, Staff food, and the organization area. Those choices settle most of the visible inconsistencies and determine the export filenames, feedback areas, kiosk labels, and server messages.

My smallest coherent set

Flytninger, Spild, Optælling, Personalemad, and Administration. These are already the dominant Danish terms behind the primary navigation.

Copy that should follow the choices

Downloaded filenames

Three Danish report flows create English filenames: transfers-*.csv, waste-*.csv, and staff-food-*.csv. The bad-delivery and own-check exports already use Danish stems. Rename these after decisions 1, 2, and 4.

Shared copy registries

Primary navigation labels are duplicated in components/app-shell.tsx, lib/sidebar-navigation.ts, and lib/feedback.ts. Apply the same selected term in all three. The feedback file also has deliberate English labels for Linear and email. Those internal labels should stay English.

Server errors

Client handlers commonly display error.message in a toast or alert. Backend vocabulary is therefore product copy. Transfer, Staff food, Scope, member, and technical validation messages need the same pass as visible components.

Do not collapse distinct concepts

Medarbejder is a Workfeed person and Bruger is an authenticated account. Workfeed Afdeling and OnlinePOS Afdeling are provider fields, while Lokation is the local site. Those differences are useful and should remain explicit.

Consistent loanwords

Dashboard, widget, feedback, kiosk, login, token, and API are used consistently enough that I did not classify them as discrepancies. They can stay unless you want a separate Danish-only vocabulary pass. Provider names and provider-owned field names also stay as written.

Coverage and method

I reviewed user-visible JSX text, labels, placeholders, accessible names, toast and alert messages, shared registries, metadata, offline copy, CSV and PDF names, Convex errors that clients can display, generated emails, and provider integration copy. Tests, generated Convex code, CSS classes, route IDs, permission IDs, and database names were excluded from language findings.
