Implementation plan

Read-only Wolt order integration

Build a forward-only Wolt Marketplace Order API integration that records order lifecycle and item facts, removes consumer PII at the boundary, and serves local Convex data to a dedicated order page, dashboards, and Count waste.

Scope confirmed Prepared 27 August 2026 Wolt API use approved Target: multi-tenant general availability

Decision

Keep Wolt orders, items, events, credentials, and daily rollups in isolated Wolt tables for v1. Do not write Wolt into salesOrders, salesLines, or salesDaily. Dashboard queries combine the current OnlinePOS daily branch with the Wolt daily branch only when the user explicitly selects Combined.

Main risk

OnlinePOS reset and reconciliation currently delete all sales rows for a location or day without a safe provider boundary. Sharing those tables could erase Wolt data, merge unrelated order identities, and double-count overlapping orders. Isolated storage avoids that migration and keeps the first release small.

1. Outcome and boundaries

The application will observe Wolt orders. Wolt Merchant remains the operational tool. The integration will not accept, reject, confirm, mark ready, replace, refund, or otherwise change an order.

Area Confirmed behavior Not in v1
Order history Forward-only from each location's activation time. Store lifecycle, basket, and item facts for 400 days. Historical import or reconstruction before activation.
Operations Read-only order list and detail. Order actions, menu writes, venue management, courier controls, or Wolt Drive.
Sales sources OnlinePOS, Wolt, or Combined. Combined is a literal sum with a duplicate warning. Cross-provider matching or heuristic deduplication.
Revenue Delivered basket after discounts, excluding delivery fees and cancelled or rejected orders. Subtract auditable refunds when the read payload exposes them. Settlement, commission, payout, or fee accounting.
Onboarding SSIO per venue and WIO bulk onboarding. Every venue maps to one organization location. Brand OAuth in v1.
Privacy Persist only order, venue, basket, status, and item facts needed by the product. Consumer name, phone, comment, address, coordinates, company or tax details, loyalty data, and raw payloads.

Success measures

  • Every valid, routed webhook is durably recorded before the HTTP 200 response.
  • Duplicate and out-of-order events converge on one current order snapshot and one correct daily contribution.
  • OnlinePOS maintenance cannot update or delete Wolt records.
  • All tenant and location checks run on the Convex server.
  • Dashboard and order-list reads never call Wolt.
  • A schema and log inspection proves that excluded PII is not persisted.

2. Wolt contract and first checkpoint

Wolt has approved this use of its API. Phase 0 is therefore a credential and behavior check, not a commercial feasibility study. If the supplied credentials do not support the approved read-only flow, stop and resolve the mismatch with Wolt before implementing order operations.

Documented facts

  • The Order API exposes GET /v2/orders/{orderId}. The documented read flow is a webhook followed by a fetch for one order. The reviewed reference does not document a list, date search, cursor, export, or history endpoint.
  • Test API base: https://pos-integration-service.development.dev.woltapi.com. Production API base: https://pos-integration-service.wolt.com.
  • OAuth 2.0 access tokens are valid for one hour. Refresh tokens are valid for 30 days, are single-use, and rotate on every refresh.
  • Webhooks are signed over the raw body with HMAC-SHA256. The signature is hexadecimal in WOLT-SIGNATURE. Wolt requires a cryptographically random secret of at least 128 bits and an HTTP 200 acknowledgement. It documents one retry after five seconds and two more at five-second intervals.
  • Requested order events are CREATED, PRODUCTION, READY, DELIVERED, and CANCELED. Webhook statuses are uppercase while the order object uses lowercase values.
  • Order id is the durable key. order_number is display-only, is a string, and can repeat. Money uses integer minor units. basket_price covers items and modifiers and excludes fees.
  • Wolt warns that fields and enum values can be added. Parsing must tolerate unknown properties and preserve an unknown status as a bounded raw value plus a normalized other value.

Phase 0 evidence to obtain

  • A test client ID and secret, one SSIO test venue, and a WIO test path.
  • Successful token exchange and GET /v2/orders/{orderId} for an event received at the test webhook.
  • Confirmation that the configured client is read-only for this product even though Wolt's restaurant guide also describes operational POS actions.
  • Actual payloads for instant, preorder, delivered, cancelled, discounted, full-refund, and partial-refund cases.
  • Webhook secret topology, event selection, replay support, numeric rate limits, and whether Menu API reads are included.

4. Architecture

1. WoltSigned order event
2. HTTP boundaryVerify raw-body HMAC and parse envelope
3. Durable inboxResolve venue, dedupe event, schedule work
4. Fetch workerRefresh token if needed and GET Order V2
5. MinimizeValidate known fields and discard PII
6. Local modelUpsert order, items, events, and daily delta
7. ReadsOrder page, dashboards, mapping, and Count waste

The HTTP path performs only work needed for safe acknowledgement. One internal mutation resolves the venue, inserts or finds the event, and schedules processing transactionally. It returns HTTP 200 after that commit, not after the Wolt order fetch. Fetch, parsing, order upsert, item replacement, and daily correction run asynchronously.

Order update rule

  1. Deduplicate the webhook by Wolt venue ID plus event ID.
  2. Fetch Order V2 using the connection for the event venue.
  3. Reject a fetched order whose venue does not match that connection.
  4. Parse into a PII-free internal value. Permit unknown JSON keys and unknown enum values.
  5. Compare modified_at with the stored order. An older snapshot may add event history but cannot replace a newer order snapshot.
  6. Compute the old daily contribution and the new daily contribution. Apply only the delta.
  7. Mark the inbox event complete. Retry retryable failures; dead-letter permanent or exhausted failures.

This delta rule handles delivered, cancelled, and later refund corrections without rebuilding a day. It also makes duplicate snapshots net to zero.

5. Data model

Every tenant-owned row includes organizationId and, where applicable, locationId. Public queries begin with organization and enforce location scope. Two global indexes are justified only for the signature-verified inbound route: venue routing and event deduplication. They are internal-only and immediately recover the tenant boundary.

Status and contribution normalization

  • Webhook CANCELED and fetched rejected normalize to terminal cancelled.
  • Fetched delivered normalizes to terminal delivered.
  • Unknown values normalize to other while retaining bounded raw text for diagnosis.
  • Delivered contribution is one order plus basket total after discounts, less a refund amount only when its source and meaning are proven.
  • Cancelled contribution is one terminal cancellation and zero revenue.
  • All other states contribute zero to delivered revenue, delivered orders, and cancellation denominator.
  • Business time is created_at for instant orders and the scheduled fulfillment time for preorders. Day bucketing uses the location timezone.

6. Security, reliability, and privacy

Inbound boundaries

  • Read the request as bytes, calculate HMAC-SHA256 over the unchanged body, decode the hex header, and compare equal-length byte arrays in constant time before parsing JSON.
  • Reject an invalid signature without logging the body. Apply a small request-size cap before allocation.
  • After signature verification, validate a narrow event envelope. Never persist the raw body.
  • Resolve Wolt venue ID through the internal route index. A missing venue goes to the bounded quarantine and raises an alert.
  • Return HTTP 200 for a duplicate already committed to the inbox. Return 200 for a newly committed event. Do not wait for the Wolt fetch.

OAuth and token storage

  • Keep Wolt client secret, webhook secret, WIO endpoint API key, and an application encryption key in Convex environment variables. Separate test and production values.
  • Encrypt access tokens, refresh tokens, and pending WIO authorization codes before storing them. Public settings queries return status and timestamps, never credentials or ciphertext.
  • For SSIO, create a high-entropy one-time state bound to organization, location, user, exact redirect URI, and a short expiry. Consume it in one server mutation.
  • For WIO, verify the X-API-Key, validate partner_venue_id against a preconfigured location mapping, durably queue the single-use code, and return quickly. Wolt documents a one-hour authorization-code lifetime.
  • Serialize refresh per connection with a mutation-acquired versioned lease. Persist the new access and refresh tokens only if the lease version still matches.
  • A crash after Wolt rotates the refresh token but before Convex commits the new one cannot be made atomic across systems. Detect the failed token set, mark the connection reauthorization_required, alert, and use SSIO or WIO to reconnect.
  • Refresh before access expiry and rotate inactive refresh tokens well before 30 days. Never request a new token for every API call.

Retries and observability

  • Retry network errors, 429, 500, and 503 with bounded exponential backoff and jitter. Respect Retry-After when present.
  • Treat malformed identifiers, venue mismatch, and persistent authorization failures as non-retryable until configuration changes.
  • Expose per-venue last event, last successful fetch, backlog, dead-letter count, token health, and bounded last error to integration managers.
  • Never put tokens, raw bodies, consumer fields, or full provider responses in logs or error strings.
  • Provide an integration-manager action to retry a dead-letter event after the cause is corrected.

Authorization

  • integrations.manage is required to connect, disconnect, retry, or edit Wolt mappings. SSIO also requires access to the selected location. Bulk WIO mapping requires all-location access.
  • sales.viewDetail plus location scope is required for the Wolt order page, items, and detailed custom datasets.
  • sales.viewAggregate or sales.viewDetail is required for aggregate Wolt dashboard metrics.
  • Every public Convex function derives the organization from Better Auth. Client-side hiding is only a usability aid.

7. Location onboarding

SSIO self-service

  1. An integration manager selects one accessible location from Administration integrations.
  2. The server creates the expiring OAuth state and returns the Wolt authorization URL using an exact allowlisted redirect URI.
  3. The callback consumes the state, exchanges the authorization code, extracts and verifies the Wolt venue ID, and creates the location connection.
  4. The activation timestamp is set when the connection becomes ready. No earlier order is claimed or imported.
  5. Repeat for every location. One venue connection never grants another location access.

Follow Wolt's SSIO flow. The settings UI shows connected venue, activation time, token health, last event, and last successful fetch, but no credential values.

WIO bulk onboarding

  1. An all-location integration manager exports or confirms the explicit mapping from internal location ID to the partner venue ID supplied to Wolt.
  2. Wolt sends one request per venue to the authorization-code endpoint described in the WIO guide.
  3. The endpoint verifies X-API-Key, resolves partner_venue_id, stores the encrypted one-hour code, schedules exchange, and returns a 2xx response.
  4. The worker exchanges each code independently. One venue failure does not block other locations.
  5. Unmapped partner venue IDs enter a bounded onboarding quarantine and alert an integration manager.

Brand OAuth remains out of scope because it is eligibility-gated and is not needed to support connecting all locations. See Wolt's Brand OAuth documentation.

8. Product behavior

Dedicated Wolt orders page

Add a main-application route, proposed as /wolt-orders, and register it in components/app-shell.tsx and lib/sidebar-navigation.ts. Final user-facing text must follow the repository's Danish terminology; this plan does not invent that copy.

  • Server-paginated and index-backed. Default to recent orders within the user's accessible locations.
  • Filters: date, location, normalized status, instant or preorder, and display order number.
  • List fields: order number, business time, location, status, type, net basket, currency, and item count.
  • Detail: item names, quantities, identifiers, line amounts, mapping state, and PII-free status history.
  • Reactive updates from Convex. No Wolt call during page load and no operational buttons.
  • Empty, loading, stale, disconnected, and partial-error states. Touch targets and tables must work on tablets and remain usable on phones.

Product mapping

Reuse the interaction pattern in components/catalog/product-form.tsx and components/catalog/online-pos-product-suggestions.ts: the select list shows suggested local products and why they match, but the user must choose and save.

  1. Build the Wolt item catalog from observed order items. If credentials grant Menu API read access, use menu identifiers to improve coverage, not as a hard dependency.
  2. Rank exact GTIN, pos_id, or SKU matches before normalized name matches. Do not silently prefer a conflicting exact match.
  3. Save a shared organization mapping when an identifier means the same product across locations.
  4. Save a location override when the same identifier conflicts. Resolution order is location exact match, then organization exact match, then unmapped.
  5. Never auto-save a suggestion. Show unmapped and conflicting items as work to resolve.

The same mapping resolver serves Wolt order detail, product dimensions in custom dashboards, and Count waste. This avoids three subtly different mapping rules.

Count waste

  • Add a per-location source setting in Administration Count: OnlinePOS, Wolt, or Combined.
  • Before a value is saved, default to OnlinePOS when connected; otherwise default to Wolt when connected. Never default to Combined.
  • The OnlinePOS loader explicitly filters salesLines.source to OnlinePOS before applying OnlinePOS mappings.
  • The Wolt loader reads only delivered Wolt item contributions in the Count business interval and applies Wolt mapping resolution.
  • Combined concatenates both mapped sources. It does not deduplicate. Show the duplicate warning next to the setting and in the resulting report context.
  • Show mapping coverage, freshness, and omitted unmapped quantities so a quiet zero cannot look complete.

9. Dashboard contract

Source-aware built-ins

Add SalesSource = onlinePos | wolt | combined to sales widget options. Persist it in WidgetInstance.options, validate it in Convex, include it in metric requests and shared-dashboard requests, and pass it to the metric computer. Existing saved widgets have no value and must continue to resolve to OnlinePOS. The add-widget dialog defaults to Wolt only when the selected scope has Wolt and no OnlinePOS connection.

Metric OnlinePOS Wolt Combined
Sales revenue Current salesDaily.revenue. Delivered net basket from woltSalesDaily. Literal sum by location, day, and currency.
Order count Current salesDaily.orderCount. Delivered Wolt orders. Literal sum. Possible duplicates remain.
Average basket OnlinePOS revenue divided by OnlinePOS orders. Wolt delivered net revenue divided by delivered Wolt orders. Total selected revenue divided by total selected orders, not an average of averages.
Wolt cancellation rate Not applicable. cancelled / (delivered + cancelled) for terminal Wolt orders. Not applicable. This metric is Wolt-only.

Combined must be chosen explicitly and must display: totals may contain the same order from both systems. No heuristic reconciliation is attempted. Render the warning from the saved widget option in edit mode, normal dashboard mode, and shared-dashboard mode. A result-contract change is not required for that static warning.

Freshness

  • OnlinePOS reads current sync status. Wolt reads each selected venue connection's last successful order fetch and error state.
  • Combined evaluates both providers only where they are configured. A missing OnlinePOS connection cannot make a Wolt-only location stale.
  • Result freshness uses the oldest relevant successful time and counts only selected provider/location errors.
  • A Wolt backlog or dead letter makes the affected location stale even if its last successful fetch is recent.

Custom datasets

  • Add woltOrders with revenue, delivered orders, cancelled orders, cancellation rate inputs, and item quantity. Dimensions include location, normalized status, order type, and business-time bucket.
  • Add woltOrderItems with net line amount, quantity, and line count. Dimensions include mapped product, observed item, location, status, and order type.
  • Detailed datasets require sales.viewDetail. Aggregate outputs accept sales.viewAggregate only when the executor cannot reveal order, item, or small-group detail.
  • Keep read caps, truncation indicators, organization checks, and location scope in the custom executor.

10. Delivery phases

Each phase has a hard exit. Do not start production ingestion until the sandbox contract is proven. Do not expose Combined until its warning and source-specific tests pass.

Phase 0: prove the approved read path

Goal. Demonstrate SSIO, WIO, signed event receipt, token rotation, and Order V2 fetch with the supplied test credentials.

Scope. Wolt sandbox, exact redirect URLs, event and secret configuration, representative payload capture in temporary development tooling only.

Constraints. No production data and no order-state mutations. Captured payloads must not enter the repository or logs.

Exit. A written contract fixture describes required non-PII fields, refund visibility, preorder fulfillment time, statuses, menu access, rate guidance, and forward-only limitations.

Phase 1: source-safe foundation

Goal. Add isolated schema, strict PII-free internal types, indexes, crypto helpers, and daily contribution arithmetic.

Likely files. convex/schema.ts, new convex/lib/woltApi.ts, new Wolt model helpers, and retention scheduling in convex/crons.ts.

Constraints. No change to existing sales table or REST meaning. Money remains integer minor units. All org records are scoped.

Exit. Parser fixtures tolerate unknown fields, reject missing required fields, discard every excluded PII field, and daily delta tests prove duplicate updates are net zero.

Phase 2: SSIO and WIO onboarding

Goal. Let authorized organizations connect every location through SSIO or WIO and see connection health.

Likely files. New convex/wolt.ts, convex/http.ts, app/organization/integrations/page.tsx, and new organization Wolt connection components.

Constraints. One-time state, redirect allowlist, encrypted tokens, WIO API-key verification, all-location access for bulk mapping, no Brand OAuth.

Exit. Replayed state and authorization codes fail, cross-location connection attempts fail server-side, concurrent token refresh yields one stored token set, and reconnect recovery works.

Phase 3: webhook and order ingestion

Goal. Receive, authenticate, queue, fetch, normalize, and persist Wolt orders with correct status and daily deltas.

Likely files. convex/http.ts, new convex/woltSync.ts, convex/lib/woltApi.ts, Wolt internal mutations, and convex/crons.ts.

Constraints. HTTP 200 only after durable queueing. No raw body storage. No provider call from reads. Forward-only from connection activation.

Exit. Valid, invalid, duplicate, out-of-order, unknown-venue, retry, dead-letter, delivered, cancelled, preorder, discount, and supported refund cases pass with exact daily totals.

Phase 4: Wolt order page

Goal. Provide a responsive, reactive, read-only order list and PII-free details for permitted locations.

Likely files. New app route and components, new public queries in convex/wolt.ts, components/app-shell.tsx, and lib/sidebar-navigation.ts.

Constraints. sales.viewDetail, server pagination and location scope, no operational controls, Danish implementation copy.

Exit. Role and location tests prevent cross-tenant and cross-location reads; phone-sized and tablet layouts expose the same safe fields; no network request reaches Wolt.

Phase 5: mapping and Count waste

Goal. Add user-confirmed Wolt product mapping and per-location OnlinePOS, Wolt, or Combined Count sales input.

Likely files. Wolt mapping queries and mutations, new organization mapping UI, components/catalog/product-form.tsx pattern reuse, convex/onlinePos.ts, and Count settings UI.

Constraints. Location override beats organization mapping. Suggestions never auto-save. Combined never defaults and never deduplicates.

Exit. Exact and name suggestions are labeled, conflicts remain unresolved until chosen, source selection produces exact quantities, and coverage/freshness warnings are visible.

Phase 6: source-aware dashboards

Goal. Expose Wolt, OnlinePOS, and explicit Combined sales metrics plus Wolt cancellation and custom datasets.

Likely files. Dashboard types, validators, registry, computers, custom executor, authenticated and shared queries, add/edit widget UI, and grid requests.

Constraints. Existing widget default remains OnlinePOS. Combined is literal addition with a warning. Permissions and source choice are validated server-side.

Exit. Revenue, order count, weighted basket, cancellation formula, currency handling, previous period, freshness, sharing, and location scope pass for all source choices.

Phase 7: production hardening and launch

Goal. Complete Wolt test cases, operational alerts, retention, support runbook, staged enablement, and production credential cutover.

Likely files. Focused tests, deployment environment documentation, health UI, runbook, cron retention, and feature-flag or connection-state gates.

Constraints. Start with internal organizations, then a small venue set, then general availability. Disconnect never deletes retained facts immediately.

Exit. Wolt QA is accepted, backlog and token alerts reach an owner, rollback is rehearsed, PII audit is clean, and production venues remain current through an observation window.

12. Rollout and operations

  1. Deploy schema and readers with Wolt hidden and no connected venues.
  2. Enable test SSIO and WIO connections. Prove event processing and PII minimization.
  3. Enable one internal production organization and a small location set at recorded activation times.
  4. Observe event lag, fetch success, token rotation, dead letters, daily corrections, and source totals through a defined monitoring window.
  5. Enable the order page, mapping, Count source choice, then Wolt dashboard choices in that order.
  6. Expand to general availability after Wolt QA, support ownership, and rollback rehearsal.

Disable and rollback

  • Disabling a connection stops new fetches and marks Wolt data stale. It does not immediately delete retained orders or daily totals.
  • Application rollback hides Wolt routes and source choices, stops Wolt scheduled work, and preserves the isolated tables for diagnosis and later resume.
  • Never roll back by deleting shared sales data or changing existing widget defaults.

Operational alerts

  • Signature failures above a low threshold.
  • Valid event for an unknown venue.
  • Oldest queued event beyond the freshness target.
  • Any dead-letter event.
  • Repeated 401, refresh lease failure, or reauthorization required.
  • No webhook or successful fetch for a connected venue beyond its expected activity window.
