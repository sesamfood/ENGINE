Convex efficiency audit

The system does not need another general cache. It needs fewer clock-based query keys, less client-driven synchronization, and narrower read sets.

Outcome

About 84% of the shown database I/O sits in three families: Workfeed synchronization, dashboard metrics, and product catalog reads.

The first implementation pass should remove hourly Workfeed runs, slow the dashboard clock from five minutes to one hour, and delete catalog payload that the UI never reads. These are direct cuts with no data-model migration.

Do not start with Next.js caching.

Convex already caches identical query results, and cached reads consume no database bandwidth. The expensive paths keep changing arguments or touching volatile and broad read sets, so they miss or invalidate that cache.

Ranked findings

Fix measured waste first

P0 · 01

Every active organization can trigger a full 91-day Workfeed shift sync each hour

very high impactsmall changehigh confidence

ActiveSyncHeartbeat calls organization.requestActiveSync hourly while the app is visible. That mutation schedules Workfeed shifts and OnlinePOS. A Workfeed run covers 30 historical days plus 60 forecast days in thirteen seven-day actions.

Evidence: components/app-shell.tsx:149-191, convex/organization.ts:82-135, convex/workfeedSync.ts:19-25. The screenshots show 16.5K syncShiftChunk calls and 44.7% of compute. Convex Insights also reports 13 development conflict-marked calls on organizationSyncActivity.

Recommendation: stop scheduling Workfeed from the client heartbeat. Keep the existing daily Workfeed cron and the manual refresh control. Move OnlinePOS incremental sync to a server interval, initially every four hours. Remove the per-tab heartbeat after the server schedule is live.

Expected direction: a continuously active organization falls from as many as 24 full Workfeed runs per day to one, a 96% reduction in active-driven full runs. Actual savings depend on app activity.

P0 · 02

The dashboard creates fresh query keys every five minutes

very high impactsmall first stephigh confidence

useDashboardNow changes now every five minutes. That value is part of every metric query. A 24-widget dashboard has eight subscriptions, so one open dashboard can create 96 time-driven query executions per hour before reactive updates from real data writes.

Evidence: lib/dashboard/use-dashboard-now.ts:5-24, components/dashboard/dashboard-grid.tsx:47-70,317-324. dashboard.getMetrics accounts for 619.34 MB of shown database I/O.

Recommendation: change the first release to an hourly bucket. Then split the contract into a date/range anchor, which changes at the relevant local day boundary, and a small integration-freshness query. Keep true time-sensitive metrics such as open Counts separate.

Expected direction: the hourly change removes 11 of 12 timer-driven executions, a 91.7% reduction in that component. A day-bound anchor removes 287 of 288 five-minute buckets for historical metrics. Writes remain reactive.

P0 · 03

Two catalog endpoints do expensive product hydration that current UI code does not need

high impactvery small changehigh confidence

catalog.listFormOptions loads up to 100 products, every product's units, unit documents, and image URLs. The form only reads categories and units; it already obtains products through catalog.listActiveProducts. Separately, count.listCountProducts hydrates up to 500 products but has no caller in the current workspace.

Evidence: convex/catalog.ts:1195-1251 versus components/catalog/product-form.tsx:284-287,348-357; convex/count.ts:448-535. The screenshots show 12.75 MB production I/O for form options and 125.89 MB combined I/O for Count products.

Recommendation: remove products from listFormOptions. Confirm no calls to count.listCountProducts after one deployed-client grace period, then delete it. Its presence in the current function spec means stale browser bundles can still call it.

P1 · 04

Volatile Workfeed run state invalidates otherwise stable roles and location mappings

high impactmedium changehigh confidence

getShiftSyncContext reads the sync status together with up to 200 location mappings and 1,000 roles. Each chunk updates the status document, so the next context query cannot reuse the stable result. The same mixing exists in getShiftRequestContext.

Evidence: convex/workfeedSync.ts:338-430. The context functions account for 167.79 MB of shown database I/O; getShiftSyncContext alone is 143.65 MB.

Recommendation: split a stable integration context—settings, mapped locations, roles—from a small volatile run-state query—token, company, success timestamp, hashes. Stable context will remain cached until configuration or employee-role data actually changes.

P1 · 05

Changed Workfeed chunks re-read and patch every shift mapping in the chunk

high impactlarger changehigh confidence

The source hash correctly skips an unchanged seven-day chunk. If one shift changes, however, upsertShiftBatch performs an indexed mapping read, a shift read, and an unconditional mapping patch per shift. Cleanup then reads the chunk mappings again.

Evidence: convex/workfeedSync.ts:934-1015,1027-1089,1161-1179,1221-1248. upsertShiftBatch accounts for 402.76 MB of shown database I/O.

Recommendation: apply cadence and context fixes first. If this remains hot, replace a changed chunk through paged range reads and an in-memory external-ID diff, so existing mappings are loaded once and unchanged rows are not patched solely for a run token. Preserve deletion detection and mutation limits.

P1 · 06

Dashboard batches repeat scope resolution and do organization-wide reads for small location scopes

high impactmedium changehigh confidence

Each widget calls resolveMetricParams, which starts by loading all organization locations. Each resolved widget also gets its own data cache. Metrics in the same batch therefore cannot share waste, shift, sales, or freshness reads. Several loaders query the full organization and filter selected locations in JavaScript even though location indexes exist.

Evidence: convex/dashboard.ts:1054-1083; convex/lib/dashboardMetrics.ts:186-229,465-487,687-705,825-843,959-980,1085-1105,1153-1176. The default dashboard places two Waste readers in different batches.
  1. Resolve scope once per unique effective range inside a batch.
  2. Share a cache among metrics with the same range and scope.
  3. Group requests by source and range instead of display position.
  4. For one or a few selected locations, query the existing location indexes; keep organization-wide queries for broad scopes.

Do not combine every widget into one giant query. That would widen the reactive read set and rerun unrelated metrics after any write.

P2 · 08

Product list and shared catalog queries use bounded but expensive N+1 hydration

medium impactmedium changemeasured

catalog.listProducts loads category, default unit, product units, ingredients, and image URL per item, even though the category hierarchy is already loaded. listActiveProductCatalog does per-product unit reads and per-unit document reads for several registration screens.

Evidence: convex/catalog.ts:742-782,795-800, convex/lib/productCatalog.ts:50-122. Catalog product and Waste catalog endpoints account for at least 69.62 MB; the dead Count product endpoint adds another 125.89 MB.

Recommendation: first return narrower shapes per flow and avoid image URLs where they are not rendered. Reuse category and unit maps already loaded in the query. Only if usage remains material, introduce a versioned, segmented catalog projection maintained by the existing catalog mutations.

P2 · 09

Multi-location reports use post-index database filters

latent scaling riskdefer until measured

Sixteen database .filter(q => ...) sites remain. The most relevant are multi-location Waste, bad delivery, Staff food, sales, and own-check reports. Convex still reads documents rejected by .filter(), so restricted-location users in a large organization may scan many irrelevant rows.

Recommendation: keep this below the measured hotspots. If Insights shows it, use compound location/status/time indexes and a bounded per-location merge strategy. Do not add indexes speculatively.

P3 · 10

Contract and scheduling hygiene should be cleaned up after the cost work

low immediate costsmall changes
  • Current production and development specs expose 16 public functions without return validators: 15 catalog functions and auth.getAuthUser. Return validators bound accidental payload growth and make contracts explicit.
  • Three cron expressions run exactly at minute zero. Convex recommends avoiding the top of the hour; move them to non-zero minutes or use intervals where exact wall time is unimportant.
  • organization.getBranding is subscribed twice in the app shell. The client may deduplicate identical watches, so verify before changing it.

Implementation sequence

Take the small cuts before structural work

Phase 1 · direct cuts

One small release

  1. Stop Workfeed from the hourly heartbeat; schedule OnlinePOS every four hours on the server.
  2. Change dashboard time bucketing from five minutes to one hour.
  3. Remove products from listFormOptions.
  4. Confirm and remove listCountProducts after stale-client grace.
  5. Use a five-minute Staff food read bucket and midnight Own-check refresh.
Phase 2 · reuse reads

Measured structural fixes

  1. Split stable Workfeed context from volatile run state.
  2. Return Count transition timestamps and stop minute polling.
  3. Resolve dashboard scope once per range and share source caches.
  4. Branch dashboard readers between location and organization indexes.
Phase 3 · only if still hot

Higher-ceremony changes

  1. Diff changed Workfeed chunks from one range read.
  2. Add a segmented catalog projection/version.
  3. Replace multi-location post-filters with indexed merges.
  4. Add explicit return validators and stagger cron minutes.

Verification plan

Compare equivalent traffic, not raw totals

Capture a seven-day baseline before Phase 1 and compare the following seven days with similar active organizations and dashboard traffic. Do not infer savings from development deploy churn.

Workfeed calls and computesyncShiftChunk should approach 13 calls per enabled organization per daily run, plus manual runs. requestActiveSync conflicts should disappear.
