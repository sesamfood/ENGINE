Executive verdict

Strong core, unsafe edges

The tenant model is sound. I found no direct cross-organization read or write bypass in the audited public functions. The urgent problems sit in delegated administration, provider snapshot cleanup, migration, and hard deletion. Those paths can expand a user's access or silently damage data inside one organization.

Strong

Tenant isolation

Server auth derives the organization. Domain indexes usually start with that ID.

Urgent

Delegated administration

A member manager can broaden their own role and location access.

Urgent

Sync safety

Workfeed treats dropped rows as deletions. One OnlinePOS migration flag flips too early.

Mixed

Historical integrity

Snapshots are common, but location and product deletion leave important gaps.

Mixed

Lifecycle

Sales and audit retention are explicit. People, files, shares, and feedback are less clear.

Release posture. Fix the two authorization paths before granting members.manage to a non-administrator. Validate and repair the OnlinePOS migration before trusting historical rollups. Make Workfeed cleanup fail closed before unattended sync is treated as authoritative.

Security model

The tenant boundary has four checks

Better Auth organizations are the tenant key. The domain schema stores that organization ID as a string because Better Auth lives in an isolated Convex component. Runtime checks provide the cross-component relationship.

What held up. Public functions generally derive organizationId from verified auth. They do not trust a client organization argument. REST policies are reloaded on each call, so revoking a role permission immediately reduces an API key.

Location access is a second boundary

Each member can have all locations, a selected list, or an operator. Kiosk accounts get one fixed location. Most domain queries call resolveLocationFilter or requireLocationAccess. Transfers are an explicit exception. Tests confirm that selected and operator scopes do not limit transfers.

Evidence: convex/lib/auth.ts:78-322, convex/access.test.ts:412-445, convex/access.test.ts:631-674.

Schema and ownership

The schema favors explicit domain tables

There is no generic record system. Tables map to restaurant operations and keep the tenant ID close to each row. Historical records often snapshot names, units, and conversion factors so later catalog changes do not rewrite the past.

Consistency model

  • Convex mutations are atomic. Indexed read-before-write checks rely on optimistic concurrency to enforce logical uniqueness.
  • Event rows snapshot display data. This keeps Transfer, Waste, Staff food, and bad-delivery history readable after catalog edits.
  • locationStock, Waste statistics, and salesDaily are materialized views. Mutations update them or schedule bounded rebuild work.
  • Own-check templates are immutable versions. Each edit closes the old version and inserts a new one.
  • Files live in Convex storage. Domain tables own references and a weekly job removes unreferenced uploads after a grace period.

Weak point. Convex document IDs do not create foreign keys. Every hard-delete path must find every reference itself. Location and product deletion do not yet do that.

Integrations and derived data

Provider data is cached before it is read

This is the right base. Online screens do not wait for Workfeed or OnlinePOS. Sync actions fetch and parse provider data, then internal mutations write local records in batches.

Schedules and retention

  • Workfeed sync runs daily at 03:17 UTC. A failed run waits for the next cron or manual retry.
  • OnlinePOS incremental sync runs every four hours. Daily reconciliation runs at 05:23 UTC.
  • Sales older than 400 days are pruned. The forward sync backfills 90 days for a newly connected location.
  • Dashboard metrics cap reads at 5,000 rows and return truncated. The UI tells users when data is limited.

Priority findings

Fix these first

P0 means the current server boundary permits privilege expansion. P1 means code can hide, duplicate, delete, or stop serving valid data.

P0
01

members.manage can assign broader roles

The Better Auth middleware requires members.manage for update-member-role. A delegated member manager can change their own role to Manager or any registered non-Administrator role. Better Auth blocks the special Administrator role, but it does not stop a jump to a broader custom role.

Smallest fix. Require roles.manage for every endpoint that selects a role. Block self-role changes unless the caller has explicit role authority.

convex/auth.ts:303-356convex/access.ts:120-127convex/auth.ts:386-400lib/auth-permissions.ts:128-132
P0
02

A restricted member manager can grant themselves all locations

setMemberLocationAccess checks the target member and organization, but never intersects the requested scope with the caller's scope. A user with members.manage can submit their own user ID and store scope: all. The next request trusts that row.

Smallest fix. Require all-location access before changing another member's scope. Reject any self-change that broadens access. A dedicated permission would make the rule easier to reason about.

convex/access.ts:694-756convex/lib/auth.ts:125-146convex/lib/auth.ts:414-441
P1
03

Workfeed can turn malformed or partial snapshots into deletions

The parser drops malformed employees, roles, and shifts. Completion then treats unseen rows as absent. A provider schema change, partial 200 response, or bad row can deactivate people, remove assignments, and delete shifts from the cache.

Smallest fix. Fail the sync if any row is malformed. Record source and accepted counts. Commit cleanup only after the snapshot passes completeness checks. Add a sharp-drop guard for empty or unexpectedly small responses.

convex/lib/workfeedApi.ts:123-214convex/workfeedSync.ts:717-781convex/workfeedSync.ts:1146-1164convex/workfeedSync.ts:1248-1265
P1
04

The OnlinePOS legacy-ID migration can duplicate old sales

Legacy unscoped line IDs are checked only while lineIdsScoped is false. The first current-window success sets that flag before the 90-day backfill completes. Older legacy rows are then missed and inserted again under location-scoped IDs. Orders and daily totals can rise twice.

Smallest fix. Keep migration mode until backfill finishes, or run a one-time ID rewrite and rollup repair. Audit production for a legacy and scoped copy of the same provider line before changing code.

convex/onlinePosSync.ts:849-891convex/onlinePosSync.ts:986-1010convex/onlinePosSync.ts:1375-1498
P1
05

Location deletion misses live references

Both delete paths check many domains, then omit own-check entries, own-check template location arrays, selected API-key policies, and pending Workfeed location arrays. The result can hide own-check history, break a whole API key, and leave active configuration pointing at a deleted ID.

Smallest fix. Use one shared deletion helper. Archive any location with history. For an unused location, scrub every configuration array and revoke a policy that would become empty. Stop or invalidate in-flight sync first.

convex/locations.ts:590-785convex/rest/locations.ts:764-974convex/ownCheckOverview.ts:371-379convex/lib/auth.ts:263-298
P1
06

Own-check history has a lifetime 2,000-version failure point

loadTemplateVersions accepts a start date but ignores it. It loads every version before the end date and fails above 2,000 rows. Old template edits can therefore break today's plan, overview, and documentation for the organization.

Smallest fix. Fetch versions that overlap the requested period, plus the predecessor needed for each template. Keep a bounded current-version read separate from historical export reads.

convex/lib/ownChecks.ts:53-78convex/ownCheckTemplates.ts:396-442convex/ownCheckOverview.ts:385-405convex/ownCheckDocumentation.ts:238-252
P1
07

Human and REST mutations have separate policy owners

masterData.ts and locations.ts reimplement logic that also exists under rest. The REST path requires all-location access for global writes and records audit events. The human path does neither for the same master-data actions, and location audit coverage also differs.

Smallest fix. Extract shared WithAuth mutations as the catalog already does. Put authorization, validation, side effects, and audit in that shared function.

convex/masterData.ts:55-460convex/rest/masterData.ts:315-946convex/locations.ts:440-785convex/rest/locations.ts:535-974
P1
08

Duplicate OnlinePOS product mappings can misstate Count waste

Several local products can map to the same provider product ID. The Count waste report builds a map by provider ID, so the last local mapping wins. Sales can be assigned to the wrong product without an error.

Smallest fix. Add an organization and provider-product index. Reject an existing owner inside the mapping mutation. Use the indexed read for an OCC-safe logical uniqueness check.

Recommended order

A small sequence that removes most risk

Close self-escalation

Split member and role authority. Require all-location access for scope changes. Add tests for self-role and self-scope attempts.

Stop silent sync damage

Fail Workfeed on rejected rows. Stage cleanup behind completeness checks. Add provider timeouts and retries.

Audit sales migration

Detect legacy and scoped duplicate line IDs in live data. Repair lines, orders, and daily rollups. Move the flag to the end of backfill.

Make deletion single-owner

Share location and master-data mutations across UI and REST. Archive locations with history. Scrub configuration arrays.

Remove lifetime query caps

Range-load own-check versions. Paginate revision detail. Split sales reroll by day.

Enforce mapping identity

Make OnlinePOS provider product mapping unique per organization and add a duplicate regression test.

Write the lifecycle policy

Decide terms for people, feedback, evidence, shares, and disconnected integrations. Add purge or anonymization jobs.

Finish operational cleanup

Unify REST issuer config, revoke kiosk sessions on password change, and review unused indexes after tracing dynamic callers.

Definition of done for the first patch

  • A location-restricted member manager cannot broaden their own location access.
  • A member manager without roles.manage cannot assign any role, including to themselves.
  • An incomplete Workfeed response cannot deactivate or delete cached records.
  • An OnlinePOS backfill cannot create a scoped copy beside a legacy line.
  • UI and REST location deletion call the same domain function and leave no unresolved configuration reference.

Audit limits

This was a read-only source audit. It did not inspect production rows, backups, deployment logs, Better Auth data, provider responses, or Vercel and Convex environment values. It did not run a load test or a live concurrency test. The OnlinePOS migration finding is conditional on legacy unscoped rows existing. Production data must confirm its current impact.
